# Buzz on Kubernetes: deployment topology

## Scope

This node documents the **Kubernetes deployment topology for the Buzz relay**, as
declared by the chart at `deploy/charts/buzz/` — its execution nodes, the mapping
of Buzz's containers/services/data stores onto them, its network, persistence and
trust boundaries, and its failure/recovery implications. It is a description of
what the chart *declares*, cross-checked against the values and templates that
render it — not a report on a live cluster.

**Two deployment layers, not one — an ambiguity this issue's Definition of Done
does not resolve.** "The Kubernetes deployment" for Buzz names two different
things depending on who is asking:

1. **The chart itself** (`deploy/charts/buzz/`) — OSS, versioned independently via
   `chart-v*` tags, published to `oci://ghcr.io/block/buzz/charts/buzz`. This is
   what any self-hoster, and this document, can actually inspect.
2. **Block's staging cluster**, provisioned by the private
   `squareup/block-coder-tf-stacks` repository (Terraform + ArgoCD) — see
   [AGENTS.md's ecosystem table](../../../../../AGENTS.md#ecosystem). That repository
   is not present in this checkout. This node cannot verify its actual topology,
   values overrides, or network posture; it can only describe the chart that
   pipeline consumes as input, and says so explicitly rather than guessing at the
   private layer.

**The launchpad-26 fork does not operate a Kubernetes deployment at all.** The
fork's own hosted deployment (`launchpad/deploy/`) runs on a single VPS via
Docker Compose, guarded by `launchpad/deploy/run.sh` to pin an immutable
`ghcr.io/launchpad-26/buzz` image. It is a separate deployment concern from this
node and is not described further here.

## Topology and execution nodes

A chart release targets one Kubernetes namespace. Within it, the chart can
render up to five kinds of workload, each an independent execution node:

| Workload | Kind | Cardinality | Enabled by |
|---|---|---|---|
| Relay | `Deployment` | `replicaCount` (or HPA-managed) | always |
| Device pairing relay | `Deployment` | `pairingRelay.replicaCount` | `pairingRelay.enabled` |
| In-cluster PostgreSQL | subchart | 1 (eval) | `postgresql.enabled` |
| In-cluster Redis | subchart | 1 (eval) | `redis.enabled` |
| In-cluster MinIO | `Deployment` | 1 (eval, `strategy: Recreate`) | `minio.enabled` |

The three bundled data-store workloads exist only in the **quickstart** profile
and are explicitly documented as eval-only, single-replica, non-HA. In the
**production** profile none of them render; PostgreSQL, Redis, and
S3-compatible storage are external managed services or self-hosted nodes
reached over the network, addressed by `externalPostgresql.url`,
`externalRedis.url`, and `s3.endpoint` respectively.

## Container/service/data-store mapping

- **Relay container** (`relay`, in the relay `Deployment`) — the single binary
  serving WebSocket, REST, and the web UI on the `app` port (3000), plus
  separate `health` and `metrics` ports. The chart's `Service` republishes all
  three ports under matching names, and an optional `Ingress` or `HTTPRoute`
  (mutually independent, either or neither may be enabled) fronts the `app`
  port for external clients.
- **Pairing relay container** (`pairing-relay`, its own `Deployment`+`Service`)
  — the stateless `buzz-pair-relay` binary from the same image, on its own
  WebSocket port. It advertises its URL in the main relay's NIP-11 document,
  but has no chart-managed `Ingress`/`HTTPRoute` of its own.
- **wait-for-bucket init container** — quickstart-only; blocks relay
  container start until the bundled MinIO bucket exists, avoiding a
  CrashLoopBackOff race against the relay's startup-fatal S3 conformance
  probe.
- **PostgreSQL** — canonical event store. External managed service in
  production; an in-cluster subchart Deployment in quickstart.
- **Redis** — backs `buzz-pubsub` fan-out. **Hard-required** whenever the
  effective minimum replica count exceeds 1; the chart **template-fails**
  rather than silently degrading if that invariant is violated.
- **S3-compatible object storage** — media blobs and Git objects/refs. Git
  state is object-store-backed per request (an ephemeral repo is hydrated from
  storage), with writer serialization via the object-store pointer CAS and
  repo-name uniqueness enforced in Postgres — so no shared/`ReadWriteMany`
  filesystem is required across replicas.
- **Git PersistentVolumeClaim** — one `ReadWriteOnce` PVC (or operator-supplied
  `existingClaim`, or an ephemeral `emptyDir` when persistence is disabled) is
  mounted **per relay replica**, holding that replica's local working copy of
  git repo state. It is not shared storage.

## Network boundaries

- **North-south entry**: an optional `Ingress` (`networking.k8s.io/v1`) or an
  optional `HTTPRoute` (Gateway API, `gateway.networking.k8s.io/v1`) can front
  the relay `Service`. Neither is required — a platform may route to the
  `ClusterIP`/`LoadBalancer` `Service` directly, or the pairing-relay `Service`,
  by its own means.
- **East-west / cluster-internal**: the relay reaches Postgres, Redis, and
  object storage over whatever network path those endpoints are configured
  with (in-cluster `Service` DNS in quickstart; external URLs in production).
  The chart does not declare or constrain that path beyond the URL/endpoint
  values an operator supplies.
- **No NetworkPolicy is rendered by this chart.** No `networkpolicy.yaml`
  template exists under `deploy/charts/buzz/templates`, unlike the sibling
  `deploy/charts/buzz-push-gateway` chart, which does define one. Segmentation
  is left to the cluster's CNI, platform-level policy, or an operator-supplied
  `extraManifests` entry.

## Persistence boundaries

Per the Backups list below, the durable state an operator must protect spans
three different kinds of storage, each with a different Kubernetes-visible
shape: a Kubernetes `Secret` value (relay private key), an external database
(PostgreSQL), an external object store (S3-compatible), and a `PersistentVolumeClaim`
per replica (git working state). None of these are backed up by the chart
itself — it declares the resources and mounts, not a backup mechanism.

## Trust boundaries and secrets handling

- The relay Pod runs as a **dedicated, non-root identity**: fixed UID/GID
  `65532`, `runAsNonRoot: true`, `seccompProfile: RuntimeDefault` at the Pod
  level, and `allowPrivilegeEscalation: false` with **all Linux capabilities
  dropped** at the container level. `readOnlyRootFilesystem` is deliberately
  `false` — the relay's git path needs a writable working directory — which is
  a real, intentional narrowing of an otherwise hardened default, not an
  oversight.
- A dedicated `ServiceAccount` is created per release (when
  `serviceAccount.create` is true); no cluster-scoped RBAC is granted by this
  chart.
- **Two mutually exclusive secret paths.** `secrets.existingSecret` names a
  pre-created `Secret` (schema in `examples/secret-sample.yaml`) that
  production/GitOps deploys **must** use. Absent that, the chart renders its
  own `Secret` (`templates/secret-chart.yaml`) that autogenerates a relay
  private key, a git-hook HMAC secret, and any in-cluster DB/Redis/MinIO
  credentials via `randAlphaNum`, persisting them across upgrades through a
  Helm `lookup` against the existing `Secret`. **That path is explicitly
  documented as unsafe under GitOps**: ArgoCD and Flux render with
  `helm template`, under which `lookup` always returns empty, so every sync
  would mint fresh random secrets. No secret *values* are reproduced in this
  node — only the mechanism and its safe/unsafe boundary.
- The two committed GitOps examples — `examples/argocd-app.yaml` (ArgoCD
  `Application`, chart pulled as an OCI artifact) and
  `examples/flux-helmrelease.yaml` (Flux v2 `HelmRelease`) — are the
  authoritative reference for how `secrets.existingSecret` is wired into a
  production install; this node does not restate their content.

## Failure and recovery implications

- **Unrecoverable-loss inventory** (from the chart README's Backups section):
  the `BUZZ_RELAY_PRIVATE_KEY` (rotating it changes relay identity — federation
  peers stop recognizing it), the PostgreSQL database (canonical event store),
  the S3 bucket (media blobs), the git `PersistentVolumeClaim` (on-disk repo
  state), and the operator's own owner private key (held outside the chart
  entirely; recovered by reinstalling with the same `ownerPubkey`).
- **Migrations and startup**: schema migrations run automatically at relay
  startup by default (`BUZZ_AUTO_MIGRATE=true`), serialized across replicas by
  a Postgres advisory lock. If an operator disables that
  (`migrate.autoMigrate=false`), the chart does **not** run migrations for
  them — the operator must run `buzz-admin migrate` before every
  install/upgrade. This matters for failure detection because the readiness
  probe checks DB *connectivity* only, not schema freshness: a pod can report
  ready against an unmigrated schema and only fail once real traffic hits it.
- **Rolling updates**: `RollingUpdate` with `maxSurge: 1`, `maxUnavailable: 0`
  — capacity never drops during a deploy. On `SIGTERM` the relay closes every
  live WebSocket with a `1012 Service Restart` frame; `drainJitterMs` (0 by
  default) can spread those closes to avoid a reconnect stampede against the
  database pool, bounded under the default 60s
  `terminationGracePeriodSeconds`.
  Every replica is single-pod-scoped for one feature: `huddleAudioAvailable`
  defaults to disabled automatically once `replicaCount > 1`, because huddle
  audio is only documented as safe for single-pod relay deployments until an
  SFU exists.
- **Disruption and scaling are opt-in, not automatic**: a `PodDisruptionBudget`
  only renders when `podDisruptionBudget.enabled` is true *and* the effective
  minimum replica count exceeds 1. The optional HPA scales on the larger of
  CPU utilization or an average-active-WebSockets custom metric — CPU scaling
  needs a cluster Metrics Server, and the WebSocket metric additionally needs a
  custom-metrics adapter (for example, Prometheus Adapter); the chart creates
  the `HorizontalPodAutoscaler` object but does not install either
  prerequisite.
- **Extension surface**: init containers, volumes, relay volume mounts, and
  image command/args can be overridden through narrow chart values without
  forking the chart; `extraManifests` can add independent cluster resources
  but cannot modify the chart-owned relay `Deployment`. The chart does not
  validate cross-field correctness of these raw fragments — an operator who
  misconfigures an extension can still break their own release.
