# Multi-community deployment

How one Buzz relay deployment serves many independent communities — the
execution nodes it runs on, which containers and data stores back it, the
network and trust boundary that keeps communities apart, and what deployment
automation governs it and recovers it from failure.

## Environment/topology and execution nodes

Three distinct execution-node shapes exist in this checkout today; the corpus's own
evidence entries above trace each claim.

1. **Local development — one developer's machine.** `docker-compose.yml` brings up
   seven containers on one bridge network (`buzz-net`): Postgres 17, Redis 7, Adminer,
   Keycloak (dev-mode), MinIO plus a one-shot `minio-init` bucket-provisioning job, and
   Prometheus. Every published port is bound to `127.0.0.1` only. The relay binary
   itself runs outside Compose (via `just relay` per the top-level `AGENTS.md`), against
   the Postgres and Redis containers.
2. **A Kubernetes cluster running the `deploy/charts/buzz` Helm chart** — one relay
   Deployment (`replicaCount`, default `1`), backed either by the chart's bundled
   in-cluster Postgres/Redis/MinIO (**quickstart** profile — single replica, no HA,
   eval-only) or by externally managed Postgres/Redis/S3-compatible storage
   (**production** profile — HA-capable at `replicaCount >= 2`, GitOps-renderable via
   ArgoCD or Flux). The chart optionally deploys a second, independent Deployment and
   Service for the device-pairing relay, using the same image.
3. **This cohort's staging Kubernetes cluster specifically** is provisioned and deployed
   by two repositories external to this checkout: `squareup/sprout-oss` builds the relay
   Docker image into an internal ECR, and `squareup/block-coder-tf-stacks` applies
   Terraform plus ArgoCD to deploy that image (via the Helm chart above) to the staging
   cluster. Neither repository is present in this checkout — see *Scope and omissions*.

`launchpad/ENVIRONMENTS.md` records that of the cohort's four named environments (local
development, a local VM harness, the shared cohort VPS, and contributors' machines),
only local development is `IMPLEMENTED` today; the others are `OPEN`. This node
describes the chart's designed topology for those environments, not a cohort
environment that is already standing on it end to end.

## Network, persistence, and trust boundaries

**Community isolation is a Host-header trust boundary, enforced once, at connection
time — "row zero."** `bind_community` (`crates/buzz-relay/src/tenant.rs`) normalizes the
request's `Host` header and looks it up against the `communities` table's
`UNIQUE(lower(host))` index; an unmapped or empty host fails closed to a generic
rejection, with **no default-tenant fallback of any kind**. Server-internal call sites
that have no inbound `Host` header (git Smart-HTTP, the localhost pre-receive hook
callback, the workflow execution sink, startup tasks) resolve their own tenant through
the identical fail-closed path, keyed off the deployment's own configured `relay_url`
authority — never a shortcut around the seam. On the read path, a client-supplied
community claim (an event's `h` tag) is recorded only as a separate `claimed_community`
trace label; the community actually used for storage and fan-out is always the
host-resolved one (`crates/buzz-relay/src/conformance/mod.rs`).

**Community creation sits above the tenant boundary, not inside it.** Every other admin
action is authorized by looking up the caller's role within the resolved community
(`relay_members`); creating a community cannot be, because its effect is the creation of
tenancy itself. `POST /operator/communities` is instead gated by the deployment-level
`RELAY_OPERATOR_PUBKEYS` allowlist (empty by default — provisioning disabled), sits
outside the Nostr event ingest data plane, and is NIP-98-authenticated
(`crates/buzz-relay/src/handlers/community_provisioning.rs`).

**Postgres write-fencing backs the boundary at the data layer for destructive
operations.** Whole-community deletion is a durable, lease/fence/checkpoint-guarded state
machine (`active -> quiescing -> fenced -> tombstone`) applied to every
community-scoped table in one atomic migration; the `communities` row itself is never
deleted, only tombstoned, so the unique host index and inbound references keep resolving
predictably (`migrations/0029_community_deletion.sql`). Archival is a lighter, separate
durable state (`archived_at`) under which a host stays reserved and continues to count
toward owner quotas (`migrations/0016_community_archival.sql`).

**Network surface.** The relay process binds four listeners: the app router on
`BUZZ_BIND_ADDR` (TCP, default `0.0.0.0:3000`), an optional app listener on a Unix domain
socket (`BUZZ_UDS_PATH`), a health-only TCP listener (`0.0.0.0:8080`), and a Prometheus
metrics TCP listener (`0.0.0.0:9102`) (`crates/buzz-relay/src/main.rs`). The chart's
`ingress`/`httproute` values are both disabled by default (`enabled: false`); an operator
supplies TLS termination and hostname routing externally when enabling either. Every
serving hostname must be seeded into `communities` before any client can reach it through
that hostname, and a deployment served without TLS additionally needs its `ws://` scheme
stated explicitly wherever shared, because the desktop client otherwise assumes `wss://`
for a scheme-less host (`launchpad/ENVIRONMENTS.md`).

**Persistence.** Git ref/object state served by the relay's git endpoint is
object-store-backed per request rather than filesystem-backed, and repo-name uniqueness
lives in Postgres — so horizontal scaling needs no shared `ReadWriteMany` volume. Each
pod's on-disk git working state is either a node-bound `ReadWriteOnce` PVC
(`persistence.git.enabled: true` — durable across pod restarts but not schedulable across
multiple nodes) or a per-pod `emptyDir` scratch volume (`persistence.git.enabled: false`),
which the chart's own values comments name as the correct choice for multi-replica HA,
because the object store and Postgres — not this disk — are the sources of truth
(`deploy/charts/buzz/values.yaml`).

**No secret values are reproduced in this node.** Env-var *names* that carry secrets
(`BUZZ_RELAY_PRIVATE_KEY`, `BUZZ_S3_ACCESS_KEY`, `BUZZ_S3_SECRET_KEY`, and the chart's
`secrets.existingSecret` keys) are named because the names themselves are the operable
contract; their values are never read or quoted here.

## Failure and recovery implications

- **Graceful shutdown is time-bounded and the chart's grace period is sized around it.**
  On `SIGTERM` the relay flips readiness to `503` immediately, waits a fixed `5s` before
  closing any listener (so Kubernetes stops routing new traffic first), then runs a
  `30s` hard-drain clock. A single WebSocket can stay open up to `35s` worst case, which
  fits inside the chart's `terminationGracePeriodSeconds: 60` with headroom — but that
  headroom assumes no `preStop` hook adds further delay.
- **HA has one hard dependency: Redis.** `replicaCount > 1` requires a reachable Redis
  for `buzz-pubsub` fan-out across pods; the chart **fails template rendering outright**
  if that invariant is violated, rather than degrading silently at runtime.
- **Migrations run automatically and can mask readiness gaps.** Schema migrations are
  embedded in the relay binary and run at startup, gated by `BUZZ_AUTO_MIGRATE` (default
  `true`) and serialized behind a Postgres advisory lock across replicas. Readiness
  probes verify only DB connectivity, not schema freshness — a pod can report healthy
  against an unmigrated schema and fail under load. Operators who disable
  `BUZZ_AUTO_MIGRATE` own running `buzz-admin migrate` themselves before every
  install/upgrade.
- **A startup-fatal storage probe trades slow rollout for safety.** Object storage
  reachability is checked at startup whenever `BUZZ_GIT_CONFORMANCE_PROBE` is enabled
  (the relay default); failure there is startup-fatal, so a pod whose S3-compatible
  backend is unreachable never becomes ready in the first place, rather than serving
  degraded.
- **What to back up, and what is safe to lose.** The chart's own backup list is four
  items: `BUZZ_RELAY_PRIVATE_KEY` (the relay's federation identity — rotating it creates
  a new identity peers will not recognize), the PostgreSQL database (the canonical event
  store), the S3 bucket (media blobs, default bucket name `buzz-media`), and — only when
  `persistence.git.enabled: true` was chosen — the git PVC. In the recommended
  multi-replica configuration (`persistence.git.enabled: false`), the per-pod git scratch
  volume is deliberately *not* a backup concern: it is disposable, and the object store
  plus Postgres are what actually need protecting. The owner private key is held by the
  operator, not the chart, and is restored by re-installing with the same `ownerPubkey`.
- **Whole-community deletion is recoverable up to a point, and says so in its own state
  names.** The deletion state machine (`active -> quiescing -> fenced -> tombstone`) is
  lease/fence/checkpoint-guarded and never removes the `communities` row, so a request
  that fails partway leaves an inspectable, resumable state rather than a half-deleted
  tenant. Archival (`archived_at`) is the lighter-weight, non-destructive alternative for
  a community that should stop serving without triggering deletion.
- **Cross-community isolation is asserted by an executable test suite, but only when run
  deliberately.** `crates/buzz-test-client/tests/conformance_multitenant.rs` implements
  (not stubs) A/B isolation tests asserting no tenant-observable state crosses the
  community boundary, but every test is `#[ignore]`-gated by default because it needs a
  running relay with two live `Host` mappings against the same Postgres and Redis; it is
  selected explicitly with `--ignored` and two `RELAY_URL_*` environment variables. A CI
  run that does not pass `--ignored` exercises none of these tests.
