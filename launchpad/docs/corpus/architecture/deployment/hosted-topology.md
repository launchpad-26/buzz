# Hosted topology

How a running instance of Buzz -- the relay and its companion services -- is laid out
across execution nodes, which containers/services map to which data stores, where the
network, persistence and trust boundaries sit, and what deployment automation is
authoritative for each of those. This node covers the deployment topology that is
actually inspectable from this repository: the OSS Helm chart under
`deploy/charts/`. It is the same shape of artifact (a Helm chart, deployed by ArgoCD to
a Kubernetes cluster) that top-level `AGENTS.md`'s ecosystem table says
`squareup/block-coder-tf-stacks` uses for Block's own staging deployment -- see
*Scope and omissions* for exactly what that connection does and does not establish.

## Environment and execution nodes

The execution node is a **Kubernetes cluster**. The chart targets two profiles selected
by chart values, not by a separate codebase:

- **Production** — external managed Postgres, Redis and S3-compatible storage; secrets
  supplied via a pre-created Kubernetes `Secret` (`secrets.existingSecret`); no
  chart-side secret generation; horizontally scalable (`replicaCount >= 2`, requires
  Redis). Deployed via ArgoCD or Flux, both of which render the chart with
  `helm template`.
- **Quickstart** — single-node evaluation only. Postgres, Redis and MinIO are bundled
  in-cluster as chart-managed subcharts/Deployments, and the chart autogenerates its own
  relay and service secrets. Not GitOps-safe and not intended to carry production
  traffic.

Two independent Helm charts exist, each its own release lifecycle and each published to
`oci://ghcr.io/block/buzz/charts/…`:

- `deploy/charts/buzz` — the relay, its optional device-pairing relay, and all
  relay-adjacent Kubernetes resources.
- `deploy/charts/buzz-push-gateway` — Buzz's APNs last-hop push-delivery gateway, a
  separate Deployment with its own dedicated database.

## Containers, services and data stores

| Component | What it is | Backing store(s) |
|---|---|---|
| `relay` container (Deployment) | Single `buzz-relay` binary: WebSocket + REST + web UI + git smart-HTTP + huddle audio, all in one process | PostgreSQL (event store, migrated via embedded `sqlx::migrate!`), Redis (`buzz-pubsub` fan-out, required once `replicaCount > 1`), S3-compatible object storage (media + git pack objects) |
| `relay` Service (ClusterIP) | Fronts the relay container's three named ports: `app` (3000 — WS/REST/web UI), `health` (8080), `metrics` (9102) | — |
| `git-repos` volume | Per-pod working-tree cache for the relay's git endpoint | `PersistentVolumeClaim` (ReadWriteOnce) when `persistence.git.enabled`, else an ephemeral `emptyDir` |
| `git-pack-cache` volume | Process-local immutable pack/index cache | Always an `emptyDir` |
| `buzz-pair-relay` container (optional Deployment) | Stateless device-pairing WebSocket relay, same image, different entrypoint | None — genuinely stateless |
| `buzz-push-gateway` (separate chart, Deployment) | APNs last-hop push delivery | Its own dedicated PostgreSQL database, reached over a network-policy-restricted CIDR list |

Object storage (S3-compatible: bundled MinIO in Quickstart, or an external provider in
Production) is the one store shared between two responsibilities — media blobs and git
pack objects — distinguished by key prefix/bucket layout rather than by separate
services. Full-text search runs inside PostgreSQL; the chart provisions no separate
search service.

## Network boundaries

- The relay `Service` is `ClusterIP` by default and is not itself a public network
  boundary.
- Public ingress is **optional and pluggable**: the chart can render either a
  Kubernetes `Ingress` (`networking.k8s.io/v1`) or a Gateway API `HTTPRoute`, neither
  enabled unless the operator opts in, both routing to the same Service ports.
- The maintained GitOps examples terminate TLS at an `nginx` `IngressClass` with
  cert-manager, and explicitly raise `proxy-read-timeout`/`proxy-send-timeout` to
  3600s — because the relay's primary protocol is a long-lived WebSocket connection,
  not short HTTP request/response.
- The device-pairing relay gets no chart-managed Ingress/HTTPRoute at all; an operator
  routes its own public hostname straight to the pairing Service.
- `buzz-push-gateway` draws its network boundary the tightest of any component here: a
  `NetworkPolicy` whitelists only DNS egress, an operator-named APNs CIDR list on 443,
  and an operator-named Postgres CIDR list on 5432, and the chart *fails to render*
  rather than default its metrics-scrape ingress open — an explicit fail-closed choice
  in the template itself.

## Persistence boundaries

Two different persistence models coexist in the same deployment:

- **Event and metadata state (PostgreSQL)** is the single canonical event store and is
  authoritative — losing it is losing history. Migrations are embedded in the relay
  binary and race-safe across replicas via a Postgres advisory lock.
- **Git object/ref state is not authoritative on any pod-local filesystem.** Every git
  request hydrates an ephemeral working tree from a manifest published to
  S3-compatible object storage, so the relay is "multi-instance-ready by construction"
  — nothing on local disk needs cross-instance coordination. This is why each replica
  needs only a `ReadWriteOnce` volume (or none at all) rather than a shared
  `ReadWriteMany` filesystem, and why losing a pod's `git-repos` PVC or its
  `git-pack-cache` causes no data loss, only a slower next hydrate.
- **Media blobs** live in the same S3-compatible bucket, addressed either `path`- or
  `virtual`-style depending on the provider.

## Trust boundaries (secrets)

No secret value is described by content here — only how each one flows.

- Every credential the relay container consumes (relay private key, git-hook HMAC
  secret, database URLs, Redis URL, S3 access/secret keys) reaches the container
  exclusively through Kubernetes `Secret` key references on the container spec, several
  marked `optional: true` so an absent key degrades a feature instead of blocking the
  rollout. None is ever a plaintext pod environment literal.
- The chart *can* generate its own Secret, but that path is explicitly documented as
  not GitOps-safe (its random-value generation is non-idempotent under the
  `helm template` rendering both ArgoCD and Flux use), and both maintained GitOps
  examples set `secrets.existingSecret` instead. Production trust boundary: an
  externally managed Secret (SealedSecrets, SOPS, External Secrets, or Vault, per the
  chart's own sample), never chart-side generation.
- `buzz-push-gateway` separates its migration trust boundary from its serving trust
  boundary: the migration Job holds DDL-capable credentials, while the runtime
  `DATABASE_URL` is documented as scoped to a role with only `CONNECT` plus DML on the
  gateway's six tables.

## Failure and recovery implications

- **Rolling updates are zero-unavailability by chart design**: `RollingUpdate` with
  `maxSurge: 1`, `maxUnavailable: 0`.
- **A relay pod's local disk state is disposable.** The only state a lost pod cannot
  regenerate by itself is the state enumerated in the chart's own backup list: the
  relay private key (rotating it changes the relay's federation identity), the
  PostgreSQL database, the S3 bucket, the `git` PVC (recoverable slowly by re-hydrating
  from object storage, per the persistence-boundary section above), and the owner's
  private key (held by the operator, not the chart — recovered by reinstalling with the
  same `ownerPubkey`).
- **Readiness is coupled to object-storage reachability.** With the relay's S3
  conformance probe at its default (enabled), a probe failure is startup-fatal and
  `/_readiness` never opens — an operator who disables that probe trades an early,
  clear failure signal for a later one on the first real storage operation.
  Independent of that probe, the chart's readiness check only verifies **database
  connectivity, never schema freshness** — an operator who decouples migrations
  (`migrate.autoMigrate=false`) and forgets to run `buzz-admin migrate` gets pods that
  report healthy while serving against a stale schema.
- **`replicaCount > 1` is an all-or-nothing invariant, not a soft recommendation.**
  Redis becomes mandatory the moment a second replica is requested, and the chart
  refuses to render (rather than silently running a partitioned deployment) if that
  isn't satisfied.
- **Autoscaling and disruption budgets are opt-in levers, not defaults.** An operator
  who wants pod-loss tolerance under voluntary disruption must enable the
  `PodDisruptionBudget` explicitly; it only renders once the effective minimum replica
  count is greater than 1.
- **`buzz-push-gateway`'s failure/recovery surface is narrower and separately owned**:
  its dedicated database and DDL/DML credential split mean a push-gateway incident does
  not, by the topology described here, touch the relay's own database or its
  credentials.

## Scope and omissions

expressed by the two OSS Helm charts in this repository (`deploy/charts/buzz` and
`deploy/charts/buzz-push-gateway`): execution nodes, the container/service/data-store
mapping, network/persistence/trust boundaries, the deployment automation that is
authoritative, and the failure/recovery implications those files document.
