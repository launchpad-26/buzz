# Template: `architecture-context`

How to author a corpus node that documents one system's **context boundary** — the
system as a single box, and the actors and external systems that interact with it from
outside. This template does not produce a policy: it produces a shape a real
architecture-context node must fill in, and this document names that shape.

## Note on this document's structure

Issue #1328's definition-of-done text — "states scope and authority/source of the
policy," "separates MUST requirements from SHOULD guidance," "defines
enforcement/checks and exception/escalation process," "links decisions or
higher-order policy instead of duplicating them" — describes a **policy/standard**
node (compare it to issues #1309 and #1312, which carry the identical four bullets and
produced `standards/confidence.md` and the still-open diagrams standard). A template is
not a policy: it does not regulate corpus-wide behaviour, and it has no MUST/SHOULD
split of its own to state. This document is built against #605's real acceptance
criterion for a template instead — *purpose, required sections, evidence expectations,
and the industry model/standard it adapts* — and the section headings below map to
those four things directly. The DoD's other bullets (one hand-authored document,
schema-valid front matter, one independently maintainable idea, traceable claims, links
instead of duplication, checked against provenance, clean validation) are generic to any
corpus node and this document satisfies them the same way any node does.

## Purpose

A node built from this template answers one question: **who and what, outside this
system, talks to it — and how?** It is the corpus's system-context layer: the outermost
of the architecture triad this batch defines (`architecture-context`, this document;
`architecture-container`, issue #1327; `architecture-component`, issue #1326), mapped
one-to-one onto the outer two levels of the C4 model's own four-level hierarchy —
system context and container — with component and code going deeper still.

A node using this template documents **one system's** boundary. If a second, genuinely
separate system's context needs documenting, that is a second node, not a second
section — the corpus's one-node-per-idea rule applies here exactly as it does anywhere
else in `launchpad/docs/corpus/`.

**Nodes authored from this template carry `type: architecture`** — the corpus-surface
enum value PRD #602 defines for architecture content — not `type: governance`. This
template document itself is `governance`, because it is a meta-document about *how to
write* an architecture-context node, not a piece of architecture content. Do not copy
this document's own front matter `type` into a node built from it.

## The industry model this template adapts

Two sources, used together rather than either alone:

**The C4 model's System Context diagram** (Simon Brown) is the notation: the system as
one box, the people and external systems around it, and nothing about the system's
internal structure. C4 is explicitly notation-independent — it mandates no fixed set of
shapes or colors — which is why *Required sections* below makes an explicit legend a
requirement rather than an assumption.

**arc42 section 3, Context and Scope**, is the prose half. It asks for two distinguishable
things: a **business context** (each communication partner, and the domain-specific
input/output exchanged with it) and a **technical context** (the channels and protocols
those exchanges actually travel over, mapped back to the same input/output). C4 draws
the boundary; arc42 says what has to be written down about everything sitting on it.

An unmerged research note (`launchpad/Research/project-documentation-templates.md`,
`launchpad-26/buzz#1466`, not yet merged — treated as `TEAM_KNOWLEDGE` throughout this
document, never as settled fact) frames the pairing as "C4 is diagrams, not prose ...
slots into arc42 §3/§5/§7 rather than competing with it." That framing holds up against
the primary sources themselves: neither one reaches into the other's territory, so a node
following this template needs both a diagram (C4) and the two-part prose context (arc42),
not one standing in for the other.

**Where the corpus's own constraints bite.** The corpus is Markdown-only today: every
non-`.md` file under the corpus root must sit in a `generated/` directory, and the
checker rejects such files there too, because no generator exists yet to prove one is a
reproducible projection rather than a hand-authored artifact wearing the right directory
name. A context diagram therefore cannot be a separate image or diagram-source file
right now. *Required sections* below requires a **Mermaid `C4Context` block embedded in
the node's own Markdown body** for exactly this reason — it is text, so it is canonical,
and it renders as a diagram wherever Mermaid is supported (GitHub included). Mermaid
documents `C4Context` as experimental and warns its syntax may still change; if it
breaks, fall back to a plain Mermaid flowchart with the same boundary/actor/system shapes
and an explicit legend, never to an image file. Any future canonical diagram mechanism
for the corpus generally — a generated rendering pipeline, for instance — belongs to
issue #1312, the open corpus-diagrams standard; this template does not anticipate its
answer and should be revisited once #1312 lands.

## Boundary against the sibling architecture templates

**This template covers the system's outside only:** the system as a single box, and the
actors, people and external systems that interact with it. It does **not** cover:

- The deployable/runnable units inside that box and the technology each one uses — that
  is `architecture-container` (issue #1327), one level inside this boundary.
- The internal building blocks within one of those containers — that is
  `architecture-component` (issue #1326), one level deeper still.
- Deployment topology or infrastructure for any of the above — out of scope for this
  whole triad; flag it against whatever template eventually owns deployment if it comes
  up while drafting.

The C4 model's System Context diagram and arc42 §3 independently draw this same line —
neither reaches past the system's external interfaces — which is the evidence behind
this boundary rather than a convention invented for this batch.

**If drafting a real context node reveals a place this boundary does not hold** —
some fact that only makes sense described as internal structure, or a container-level
concern arc42 §3 actually claims for itself — that is a defect in this template or in a
sibling's, not something to route around silently. Fix this document if it is the
one that is wrong; file a new issue against parent PRD #605 if a sibling template needs
to change, since this template has no authority to edit another node's file.

## Required sections

A node built from this template MUST contain the following. These are structural
requirements on the node's shape, not a corpus-wide MUST/SHOULD policy — see *Note on
this document's structure* above for why this document does not carry one of those.

1. **A purpose and boundary statement.** One paragraph naming the system in scope and
   stating explicitly that the node covers context only — no internal structure. A
   reader arriving without prior context needs to know what they are and are not about
   to read before the diagram.

2. **A System Context diagram**, as a fenced Mermaid `C4Context` block in the node's own
   body (see *Where the corpus's own constraints bite* above for why this is the only
   canonical form available today). The diagram MUST show the system as a single
   `System_Boundary` (or the top-level system element if no internal boundary is drawn),
   every external `Person` and `System_Ext` the system exchanges anything with, and a
   `Rel` for each interaction.

3. **A notation legend.** Because C4 is explicitly notation-independent, a diagram alone
   does not tell a reader what a box, an arrow or a boundary means in *this* document. A
   short legend — even one line naming the Mermaid element kinds used — is required
   alongside the diagram, not assumed from familiarity with C4.

4. **A business context section** — one entry per external actor or system named in the
   diagram, stating the domain-specific input and/or output it exchanges with the system
   in scope. arc42 recommends a table; a table is the natural fit here too, one row per
   communication partner.

5. **A technical context section** — for each communication partner in the business
   context section, the channel, protocol or transport actually used, mapped back to the
   domain-specific input/output it carries. This is where "how" lives; the business
   context section is deliberately silent on it.

6. **An evidence ledger entry for every actor, system and interaction claim** that a
   reader could check — a real API route, a config value naming an external host, a
   deployed integration. Follow `launchpad/docs/corpus/AGENTS.md`'s FACT/INFERENCE/
   TEAM_KNOWLEDGE rules exactly as any other corpus node does; this template adds no
   second evidence contract.

7. **A scope-and-omissions section** naming, explicitly, that internal structure is out
   of scope and where it is (or will be) covered — the sibling `architecture-container`
   and `architecture-component` nodes for the same system, once they exist, or the
   relevant issue if they do not yet.

## Evidence expectations

Two things are specific to a context node and worth stating plainly, on top of the
general FACT/INFERENCE/TEAM_KNOWLEDGE rules `AGENTS.md` already owns:

- **"This actor/system exists and talks to us" is a behaviour claim.** It needs
  executable evidence — a route handler, a client configuration, a deployed
  integration's config — not a decision record and not a diagram from a design
  discussion. `standards/decision-references.md`'s behaviour-versus-intent test applies
  here unchanged: if the code and a design document disagreed about who calls the
  system, the code is the one a reader would call correct.
- **"This is the right boundary to draw" can legitimately be an INFERENCE.** Deciding
  what counts as external versus internal sometimes takes judgement the cited sources do
  not fully close on their own — this document's own boundary claim above is exactly
  that kind of entry, at confidence `0.8`. Rate it honestly per
  `standards/confidence.md`'s bands rather than defaulting to FACT because the
  conclusion feels solid.

## Relationships

**Checked, not assumed absent.** Per `AGENTS.md`, "no relationships, because nothing
exists to point at" is the exact false justification this corpus has already produced
twice, so this section names what was actually checked: at the recorded revision,
`origin/launchpad`'s corpus tree carries `corpus-agents`, `corpus-readme`,
`corpus-standard-confidence` and `corpus-standard-decision-references`, and no other
node. A `references` edge from this template to `corpus-agents` would validate today —
this template's evidence-expectations section leans on `AGENTS.md`'s rules directly.

**This template declares none anyway**, for the same reason `standards/confidence.md`
and `standards/decision-references.md` already give for themselves: the edge that would
matter most is to the sibling architecture templates (`architecture-container`,
`architecture-component`) this document repeatedly points at by issue number, and none
of them exists as a merged node yet — a `relationships[].target` naming an id nothing
carries is a hard validation error. Adding a solitary `references` edge to
`corpus-agents` now and the real sibling edges later, in two separate passes, is a
weaker record than adding the whole set once the triad is complete. The first sibling
template to merge is the moment to revisit this.

**A node built from this template** should expect to declare `part-of` (pointing at
whatever capability or system-level node the context belongs to, once one exists) and
possibly `references` toward an interfaces-events node describing a protocol named in
its technical context section — this template does not mandate specific edges, because
the corpus is still too sparse for a rule about what must exist to make sense.

## A minimal worked skeleton

Illustrative only — this is not itself a validated corpus node, and the ellipses are not
literal.

```markdown
---
id: architecture-context-<system-slug>
type: architecture
status: draft
origin: launchpad
audiences:
  - agent
  - developer
  - reviewer
evidence:
  - statement: "This node was authored and checked against repository revision <sha>."
    entry_class: FACT
    evidence:
      - "commit <sha>"
  - statement: "<system> exposes an HTTP webhook endpoint that <external system> calls."
    entry_class: FACT
    evidence:
      - "<path/to/the/route/handler>"
---

# <System> — architecture context

## Purpose and boundary

One paragraph: what <system> is, and that this node covers only its external boundary.

## System context diagram

\`\`\`mermaid
C4Context
    Person(user, "End user")
    System_Boundary(sys, "<System>") {
    }
    System_Ext(ext, "<External system>")
    Rel(user, sys, "Uses")
    Rel(sys, ext, "Calls", "HTTPS/JSON")
\`\`\`

**Legend:** `Person` = a human actor. `System_Boundary` = the system this node
documents. `System_Ext` = an external system. `Rel` = an interaction, labelled with its
nature and (where relevant) its transport.

## Business context

| Partner | Exchanges |
|---|---|
| End user | ... |
| <External system> | ... |

## Technical context

| Partner | Channel/protocol | Carries |
|---|---|---|
| End user | ... | ... |
| <External system> | HTTPS/JSON | ... |

## Scope and omissions

This node covers <system>'s external context only. Its containers are documented in
<link once it exists>; its components are not documented at this layer.
```

## Scope and omissions

**This document covers** the purpose of an `architecture-context` corpus node, the
industry model it adapts, its boundary against the sibling architecture-container and
architecture-component templates, its required sections, what evidence a context node
needs, and what relationships this template document itself does and does not declare.

**It does not cover, and these are gaps rather than silence:**

| Not covered here | Owned by |
|---|---|
| Containers inside the system boundary | `architecture-container`, issue #1327, unmerged |
| Components inside one container | `architecture-component`, issue #1326, unmerged |
| The corpus's general evidence contract and citation shapes | `launchpad/docs/corpus/AGENTS.md`, `launchpad/project-intelligence/CONTRACT.md` §3 |
| The `confidence` field's meaning and bands | `launchpad/docs/corpus/standards/confidence.md` |
| Citing an accepted decision as evidence | `launchpad/docs/corpus/standards/decision-references.md` |
| A canonical diagram mechanism for the corpus beyond text-embedded Mermaid | Issue #1312, unmerged |
| Creating, updating and retiring any corpus node, including one built from this template | `launchpad/docs/corpus/AGENTS.md` |

**Expected but not verified when this node was written:**

- **No real `architecture-context` node has been built from this template yet.**
  Whether the required-sections list is actually sufficient, or misses something only a
  real system's context surfaces, is untested. The first node built from this template
  is the real test of it.
- **Mermaid's `C4Context` rendering was not exercised inside this repository's own

- **No sibling architecture template (#1327, #1326) was read as a finished document**,
  because neither is merged. The boundary section above is checked against arc42 and C4
  directly, not against the siblings' own text, so a divergence discovered once they
  land is a real possibility this document cannot rule out today.
