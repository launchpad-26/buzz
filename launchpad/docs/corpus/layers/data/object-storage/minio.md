# MinIO / S3-compatible object storage

The **datastore-level** view of the S3-compatible object store that
[`architecture-containers-object-storage`](../../../architecture/containers/object-storage.md)
already inventories as one container: what technology backs it in each
context this repository actually provisions, its two disjoint key
namespaces at a structural (not domain) grain, how it is attached to, and
what operational characteristics the codebase itself relies on. This is not
a second container inventory — the container node's existence, technology
name, and one-line responsibility/communication edges are not repeated
here, only linked. It is also not a full per-namespace reference: the
media namespace and the git-CAS namespace each warrant their own deeper
document (see *Scope and omissions*), and this node deliberately stops at
the coarse two-namespace split needed to describe the shared store
honestly.

## Store classification

**Authoritative.** No SQL migration in this repository defines an
object-store-backed table, and neither of the store's two consumers falls
back to or caches through another datastore (Postgres via `buzz-db`, Redis
via `buzz-pubsub`) for the bytes it writes here. Once a blob, pack, or
manifest is written, this store is where it lives — not a cache in front
of another source of truth, not a derived projection, and not a transport
buffer.

## Technology & attachment profile

An S3-compatible endpoint reached through the `rust-s3` crate. **MinIO is
this repository's own implementation choice in every environment it
actually provisions** — the `minio` service in `docker-compose.yml` for
local development, and the eval-only bundled MinIO in
`deploy/charts/buzz`'s quickstart Helm profile — while production
deployments point the same `BUZZ_S3_*` attachment surface at an externally
managed S3-compatible service instead (the chart's own README documents
Railway Storage Buckets as one such provider). The connection shape and
credential-resolution chain (static keys versus the AWS default credential
chain) are container-level facts already documented by
`architecture-containers-object-storage` and are not restated here.

One addressing-style detail is specific to MinIO rather than to the S3
protocol generically: `BUZZ_S3_ADDRESSING_STYLE` defaults to `path`
(`{endpoint}/{bucket}/{key}`), and both `.env.example` and the Helm chart's
README state this default exists *because* bundled MinIO's local DNS setup
does not resolve bucket-as-subdomain hostnames — `virtual` addressing is
reserved for providers whose DNS does. A deployment that swaps MinIO for a
provider requiring virtual-hosted addressing must change this one setting;
nothing else in the attachment surface is MinIO-specific.

## Key-namespace inventory

Two disjoint top-level namespaces share the one bucket, each owned by a
different consumer. This is a structural split only — what kind of thing
lives in each namespace — not the fine-grained per-key-class detail either
consumer's own document should carry (see *Scope and omissions*).

| Namespace | Owning consumer | Structural shape | Notes |
|---|---|---|---|
| Media | `buzz-media` (Blossom) | `{sha256}.{ext}` blobs, `{sha256}.thumb.jpg` thumbnails, `_meta/{community}/{sha256}.json` sidecars, `_uploads/{community}/{sha256}/{ulid}.json` auxiliary records, plus an `unknown` catch-all | Classified by `crates/buzz-media/src/bucket_index.rs`'s `classify_key`. |
| Git CAS | `buzz-relay`'s git-on-object-storage path | `packs/<sha256>` and `manifests/<sha256>` content-addressed objects, `idx/<pack_digest>` derived sidecars, `repos/<community>/<owner>/<repo>/pointer` mutable per-repo pointers | Key shapes defined in `crates/buzz-relay/src/api/git/store.rs` and `crates/buzz-relay/src/api/git/manifest.rs`. |

## Migration / schema-versioning mechanism

None exists, in the sense `buzz-db`'s embedded `sqlx::migrate!` is one. No
migration file under `migrations/` references the object store, and both
namespaces' key shapes evolve as ordinary source-code changes to their
respective key-construction functions (`bucket_index::classify_key`,
`manifest::pointer_key`, `Store::content_key`). Neither namespace's
classifier silently reinterprets a key shape it does not recognize as
belonging to a known class — an unrecognized media key falls to `Unknown`
rather than being coerced, keeping any usage accounting built from the
classifier loud instead of silently wrong on a key-shape change.

## Access-pattern summary

Each consumer talks to the store through its own client rather than a
shared abstraction: `buzz-media`'s `MediaStorage` (`crates/buzz-media/src/storage.rs`)
wraps one `rust-s3` `Bucket` for the media namespace; `buzz-relay`'s git
path (`crates/buzz-relay/src/api/git/store.rs`) constructs its own,
separate `rust-s3` `Bucket` client for the git-CAS namespace, reusing only
`buzz_media::config::S3AddressingStyle` as a shared type rather than
sharing the client itself. Both namespaces are accessed exclusively as flat
key-value objects — `get`/`put`/`head`/`delete` and their streaming
variants — with no query layer, no secondary index, and no cross-namespace
listing: `buzz-relay`'s hourly `storage_sweep` (cited by
`architecture-containers-object-storage`) is the one component that lists
the whole bucket, for usage metrics only, and can be disabled entirely via
`BUZZ_STORAGE_METRICS=off`.

## Operational characteristics the technology itself provides

- **Health/connectivity probe.** `MediaStorage::ping` performs a
  single-item bucket listing rather than calling a lighter-weight
  liveness primitive — the `rust-s3` client this codebase uses exposes no
  cheaper connectivity check.
- **Versioning detection, not prevention.** `rust-s3` exposes no
  `GetBucketVersioning` call, so `MediaStorage::bucket_versioning_detected`
  writes and inspects a short-lived probe object instead, relying on the
  fact that a versioning-enabled (or versioning-suspended) bucket stamps
  new writes with a version id. `buzz-deletion`'s bulk-delete path calls
  this probe before proceeding and permanently refuses a deletion request
  if it detects versioning, because a versioned bucket's `DeleteObjects`
  only inserts delete markers rather than proving logical absence — this
  is a wired-in safety check, not merely a documented risk.
- **A MinIO-specific delete quirk, absorbed rather than surfaced.**
  `MediaStorage::delete_objects`'s own doc comment records that historical
  MinIO releases report an already-absent key as a `NoSuchKey`/`NoSuchVersion`
  *error* rather than a successful no-op delete; the function folds that
  outcome into the same `already_missing` result used for any backend, so
  idempotent checkpointed retry behaves identically on MinIO and on any
  other S3-compatible target.
- **No lifecycle/TTL policy at the datastore level.** No S3 lifecycle rule
  or object-expiration configuration was found across `buzz-media`, the
  git object-storage path, the Helm chart, or the environment templates.
  The only retention mechanism is `buzz-deletion`'s application-driven,
  whole-community bulk delete — a datastore consumer's decision, not a
  bucket-level policy this store enforces on its own.
- **Create-only writes are the git-CAS namespace's consistency mechanism.**
  Pack and manifest writes use `If-None-Match: *` (never overwrite an
  existing key), and pointer updates use conditional `PUT` (compare-and-swap)
  with a `412` response treated as the semantic `LostRace` outcome rather
  than an error — a design that depends on the backing S3-compatible
  implementation honoring conditional-write preconditions correctly, which
  this document does not independently verify beyond citing the code that
  relies on it.

## Tenancy & security boundaries

Both namespaces follow the same shape: content-addressed bytes are shared
CAS with no tenant identifier in the key itself, gated by a separate,
tenant-scoped indirection key that controls whether a given tenant can
*resolve* that content at all.

- **Media:** blob/thumbnail bytes (`{sha256}.{ext}`, `{sha256}.thumb.jpg`)
  carry no community identifier and are shared, deduplicated CAS across
  every community. `MediaStorage::sidecar_key`'s
  `_meta/{community}/{sha256}.json` key is the tenant read gate — a
  community can only resolve a blob's metadata (and therefore serve it)
  through its own sidecar key, independently of whether the same bytes
  exist for another community.
- **Git CAS:** pack, manifest, and idx objects (`packs/`, `manifests/`,
  `idx/`) likewise carry no community identifier and are shared CAS.
  `manifest::pointer_key`'s `repos/<community>/<owner>/<repo>/pointer` key
  is the community-scoped indirection point — its own doc comment states
  this keeps the repo-local subtree "under the server-resolved community
  boundary" while the shared CAS objects it points into stay outside that
  scoped namespace.

Authorization and content validation for the media namespace's write path
(the Blossom `kind:24242` auth event, magic-byte MIME sniffing) are
documented in full by `architecture-containers-object-storage` and are not
repeated here.

every environment this repository actually provisions it, versus an
externally managed S3-compatible service in production), its store
classification, a coarse two-namespace structural split, its (non-)migration
mechanism, its cross-consumer access pattern, the operational

**On `type: layers` versus the datastore template's own suggestion.**
`launchpad/docs/corpus/templates/datastore.md` states that a real instance
node written from it "most plausibly takes `type: architecture`," on the
grounds that `node.schema.json`'s enum has no finer-grained member
distinguishing a container-, component-, or datastore-level structural
view from one another. This node instead uses `type: layers`, following
the precedent set by this same directory's two sibling documents
(`blossom-storage.md`, issue #1067, and `git-objects.md`, issue #1069),
both of which made the identical choice for the identical reason: for
consistency across `layers/data/object-storage/`, rather than each
document in that directory re-deciding its `type` independently. Per
`standards/taxonomy.md`'s guidance to disclose an imperfect fit rather
than silently pick, this is named here as an open tension, not a settled
resolution — `type` may be revised later without disturbing this node's
permanent `id`, should a corpus-wide pass resolve which of the two enum
values `layers/data/` documents should actually carry.
