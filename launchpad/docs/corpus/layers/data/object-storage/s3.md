# Datastore backend: AWS S3

This node documents what is specific to **real AWS S3 (or an AWS-API-compatible
managed provider)** as the physical backend satisfying the shared S3-compatible
object-storage container's interface — credential resolution, signing
requirements, addressing style, and the operational guarantees and hazards AWS
itself publishes for the service. It zooms into the already-merged container-level
node
[`architecture-containers-object-storage`](../../../architecture/containers/object-storage.md)
(id `architecture-containers-object-storage`), which names the bucket's
existence, its shared use by Blossom media and git, and states that production
deployments point at "an externally managed S3-compatible service (AWS S3,
Railway Storage Buckets, or similar)" without detailing any one of those
choices — this document is that detail, for the AWS S3 choice specifically.

## What this document is not

It is **not** a second copy of the container node's own technology summary —
that is linked above, not repeated. It is **not** the per-consumer key
namespace or access-pattern detail: `buzz-media`'s Blossom key taxonomy and
`buzz-relay`'s git object/manifest/pointer namespace are already documented in
full, per consumer, by
[`blossom-storage.md`](./blossom-storage.md) (#1067) and
[`git-objects.md`](./git-objects.md) (#1069) — both drafted, at the time of
writing, in the still-open pull request `launchpad-26/buzz#1873` and not yet
merged to `origin/launchpad`, so this node cannot yet declare a corpus
`relationships` edge to either (see *Scope and omissions*). It is **not** the
MinIO backend option — that is `minio.md` (#1071) — and it is **not** the
generic, backend-independent description of the object-storage *role* the
container fills — that is `role.md` (#1073). Neither sibling has an open pull
request at this node's authoring time, so their boundaries against this node
are stated here from first principles, the same honest-gap pattern
`templates/datastore.md` itself uses for its own unread sibling template
(#1333): re-check once they land.

## Store classification

**Authoritative**, restated briefly and not re-derived: the object store is the
sole durable location of both Blossom blob bytes and git pack/manifest/pointer
objects, regardless of which S3-compatible technology physically serves the
configured bucket. This fact is backend-agnostic — true of a MinIO-backed
deployment exactly as it is true of an AWS-S3-backed one — so its full
justification (no SQL migration defines a media table; the design proof for
git-on-object-storage) lives in `blossom-storage.md` and `git-objects.md`, not
here.

## Technology & attachment profile

Both `MediaStorage::new` (`crates/buzz-media/src/storage.rs`) and
`GitStore::new` (`crates/buzz-relay/src/api/git/store.rs`) build their
`rust-s3` client identically: static `access_key`/`secret_key` credentials
when both are configured (the common shape for MinIO, or any static-key
deployment), or, when both are unset, the AWS default credential chain —
environment variables, a shared AWS profile, a web-identity token (IRSA on
EKS, via `AssumeRoleWithWebIdentity`), the ECS container credential provider,
or EC2/EKS instance metadata, in that order. This is what lets a relay pod
attach to real AWS S3 using its own IAM role rather than a long-lived static
key pair — a deployment option that has no equivalent for the bundled MinIO
container, which this codebase always reaches with static credentials
(`crates/buzz-media/tests/static_creds_minio.rs` exercises exactly that
round trip).

**Region and signing.** `MediaConfig::s3_region`'s own doc comment states the
configured region "must match the region of `s3_endpoint` for real AWS S3,
otherwise requests are signed with the wrong credential scope and AWS rejects
them." The default value (`us-east-1`) exists "to preserve MinIO/local
behavior, where the value is not meaningfully checked" — MinIO does not
enforce SigV4 region-scope matching the way real AWS S3 does, so a region
mismatch that is silently tolerated locally becomes a hard signing failure
against production AWS S3.

**Addressing style.** The Helm chart's own addressing table recommends
`virtual` (bucket-in-hostname) addressing for "AWS-style providers," versus
`path` (bucket-in-URL-path) for "Bundled MinIO and endpoints whose DNS does
not resolve bucket subdomains." `S3AddressingStyle`'s own doc comment
describes `Virtual` as "the standard S3 form." Nothing in this codebase
enforces `virtual` addressing for an AWS S3 endpoint at the type level — an
operator sets `BUZZ_S3_ADDRESSING_STYLE` to match whichever provider is
actually configured — but `path` style against real AWS S3 is not the
provider's own documented default the way it is MinIO's.

## Operational characteristics AWS S3 itself provides

- **Strong read-after-write consistency.** AWS's own user guide states S3
  "provides strong read-after-write consistency for PUT and DELETE requests
  of objects in your Amazon S3 bucket in all AWS Regions," covering new-object
  writes, overwrites, and deletes, and that "updates to a single key are
  atomic." This codebase does not re-implement or re-verify that guarantee —
  it is a property AWS publishes for the service, relied on implicitly by
  every content-addressed, create-only write path documented in
  `blossom-storage.md` and `git-objects.md`. Whether every other
  S3-compatible provider this codebase can be pointed at (MinIO included)
  publishes the identical guarantee is not established by this node.
- **Optional bucket versioning is a real, guarded-against hazard.** AWS
  documents S3 Versioning as an explicitly-enabled, opt-in bucket feature.
  `MediaStorage::bucket_versioning_detected` (`crates/buzz-media/src/storage.rs`)
  probes for it by writing and reading back an object's `version_id`, and
  `crates/buzz-deletion/src/lib.rs` calls that probe before any
  whole-community deletion and treats a positive result as a permanent,
  unrecoverable failure — "bucket versioning detected; deletion cannot prove
  logical absence with delete markers" — rather than attempting the delete
  regardless. This is the concrete, code-level consequence of pointing this
  container's production configuration at a real AWS S3 bucket that has ever
  had Versioning turned on; the full deletion-pipeline mechanics are
  `blossom-storage.md`'s to document, not restated here.

## Access patterns and schema/namespace: deferred, not repeated

The bucket's key namespace (`{sha256}.{ext}`, `{sha256}.thumb.jpg`,
`_meta/...`, `_uploads/...` for media; `packs/...`, `manifests/...`,
`idx/...`, `repos/.../pointer` for git) is defined entirely by the client
code in `buzz-media` and `buzz-relay`'s `api::git` module, not by which
S3-compatible technology serves the bucket — the same `rust-s3` method calls
(`put_object_with_content_type`, `get_object`, conditional `PUT`s, and so on)
execute identically against AWS S3 or MinIO. This node therefore states no
namespace or access-pattern table of its own: see `blossom-storage.md` for
the Blossom media namespace and access pattern, and `git-objects.md` for the
git pack/manifest/pointer namespace and access pattern, once both are merged.

## Tenancy & security boundaries

The tenant boundary itself (community-scoped sidecar keys for media,
community-scoped pointer keys for git) is enforced in client code and is
identically true regardless of backend — documented in full by
`blossom-storage.md` and `git-objects.md`. What is specific to AWS S3 here is
the **credential** boundary: a production deployment backed by real AWS S3
can attach via a Kubernetes service account's IAM role (the AWS default
credential chain, including IRSA-on-EKS web-identity assumption) rather than
distributing a long-lived static access-key/secret-key pair — an option that
does not apply the same way to the bundled MinIO container, which this
codebase's own tests and local `.env.example` configuration always reach with
static credentials.

## Failure behavior

Beyond the versioning hazard named above, real AWS S3 introduces one failure
mode that a locally-tolerant MinIO configuration does not: a region/endpoint
mismatch causes AWS to reject the request's SigV4 signature outright
("otherwise requests are signed with the wrong credential scope and AWS
rejects them," per `MediaConfig::s3_region`'s own doc comment), whereas the
same mismatch against MinIO's default region handling is "not meaningfully
checked." An operator pointing this container's `BUZZ_S3_*` configuration at
AWS S3 for the first time is more likely to hit this failure than one running
against the bundled MinIO container, precisely because MinIO does not enforce
the check that surfaces it.
