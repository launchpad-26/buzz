# Desktop: client-side navigation

One paragraph up front, per this node's adapted template: this document
describes the desktop app's client-side routing and navigation layer inside
the `architecture-containers-desktop` container -- what routes exist, how
navigation is invoked and guarded, how back/forward works, and specifically
how navigation state behaves across a community switch (the desktop app's
`AppReady`/`communityKey` remount boundary, described at the container level
by `architecture-containers-desktop` but not detailed there). It answers: if
I add a new screen or need to navigate to one programmatically, what already
exists, and what happens to the URL/history when the active community
changes underneath the app.

## Responsibility

The desktop app's navigation layer is responsible for: defining the app's
routable screens, translating imperative "go to X" calls from the rest of the
UI into router state changes, gating those changes through a single
navigation-guard checkpoint, and keeping navigation history usable (OS-style
back/forward, including hardware mouse buttons and macOS trackpad swipes)
across the app's single-page lifetime -- including across a community
switch, which remounts most of the React tree but not the router itself.

## Public interface

| Item | Kind | Contract | Evidence |
|---|---|---|---|
| `routes` | virtual route table | Declares the app's twelve routes (index, `/agents`, `/pulse`, `/reminders`, `/settings`, `/workflows`, `/workflows/$workflowId`, `/projects`, `/projects/$projectId`, `/messages/new`, `/channels/$channelId`, `/channels/$channelId/posts/$postId`), all children of one root route rendering `AppShell`. | `desktop/src/app/routes.ts`, `desktop/src/app/routes/root.tsx` |
| `router` | module singleton | The one `@tanstack/react-router` instance for the app's lifetime; hash-based history, path-keyed scroll restoration. Imported directly (not via context) by code that needs to navigate outside a component, e.g. `App.tsx`'s `transitionCommunity`. | `desktop/src/app/router.tsx` |
| `useAppNavigation()` | hook | Returns every named navigation action (`goHome`, `goChannel`, `goProject`, `goWorkflow`, `goSettings`, `openSearchHit`, etc.) as stable callbacks; every action is routed through one internal `commitNavigation` that no-ops on an unchanged destination and consults the navigation guard before calling the router. | `desktop/src/app/navigation/useAppNavigation.ts:24-479` |
| `allowNavigation`, `registerNavigationGuard`, `traverseHistory` | functions | A single-slot-stack guard checkpoint: any code holding an unsaved-changes-style concern can register a guard that vetoes the next navigation or history traversal; only the most recently registered guard is consulted. | `desktop/src/app/navigation/navigationGuard.ts` |
| `useBackForwardControls()` | hook | Wires OS-style back/forward: keyboard chords (`Cmd+[`/`Cmd+]` on macOS, `Alt+←`/`Alt+→` elsewhere) and, in the Tauri build, a native `mouse-nav` event for mouse button 4/5 and trackpad swipes that a macOS WKWebView does not otherwise deliver to the DOM. Tracks forward-availability itself via a history-index key map, since the router does not expose it. | `desktop/src/app/navigation/useBackForwardControls.ts`, `desktop/src/app/navigation/backForwardChords.ts` |
| `deriveShellRoute(pathname)` | function | Maps the current pathname to the shell's selected sidebar view and, for a channel route, the decoded channel id -- the read side that keeps `AppShell`'s selection state in sync with the URL. | `desktop/src/app/AppShell.helpers.ts:217-268` |
| `loadCommunityDestination`, `saveCommunityDestination`, `markPendingCommunityRestore`, `consumePendingCommunityRestore` | functions | Persist and retrieve one last-visited destination (home, or a channel) per community id in `localStorage`, so a community switch can restore where the user left off in that community. | `desktop/src/features/communities/communityNavigationStorage.ts` |

  `architecture-containers-desktop` for that; this node covers only its

## Scope and omissions

**This node covers** the desktop app's client-side routing and navigation:
the route table and router singleton, the single imperative navigation
surface (`useAppNavigation`) and its guard checkpoint, keyboard/mouse
back-forward support, the read-side mapping from URL to shell selection
state, and -- specifically requested by this task -- how navigation state
behaves across the `AppReady`/`communityKey` remount boundary described in
this repository's root `CLAUDE.md` ("Community Switching"): the router
itself is a module-level singleton that is *not* torn down or recreated when
`communityKey` changes and `AppReady`/`CommunityQueryProvider` remount, and
both community-switch code paths (`App.tsx`'s onboarding-driven
`transitionCommunity` and `useCommunityNavigationTransitions`'s
sidebar-driven path) explicitly navigate the shared router Home and then
restore a per-community saved destination, rather than relying on any
remount to reset navigation state.
