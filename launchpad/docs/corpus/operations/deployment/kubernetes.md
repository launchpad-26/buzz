# Preparing a Kubernetes cluster for Buzz: how-to

How a cluster operator prepares and verifies the Kubernetes-cluster side of a Buzz
relay deployment via the chart at `deploy/charts/buzz` — prerequisites, namespace and
secret setup, the objects the chart's templates produce, exposure and probe
consequences, persistence, and scaling constraints — performed once per cluster or
per release, before or immediately after the chart itself is installed.

## Before you start

- `kubectl` access to the target cluster with permission to create Namespaces,
  Secrets, ServiceAccounts, Deployments, Services, PersistentVolumeClaims, and, if
  used, Ingress or HTTPRoute, PodDisruptionBudget, HorizontalPodAutoscaler and
  ServiceMonitor objects in the target namespace.
- A decision on **profile**: production (external managed Postgres/Redis/S3-compatible
  storage, `secrets.existingSecret`) or quickstart (in-cluster Postgres/Redis/MinIO,
  chart-autogenerated secrets, single replica, eval only). These steps assume
  production is the one intended to be GitOps-managed; quickstart's bundled services
  are explicitly documented as not GitOps-safe.
- If exposing the relay through classic Ingress: an Ingress controller already
  installed in the cluster, and its `IngressClass` name known.
- If exposing through Gateway API instead: the Gateway API CRDs and a compatible
  Gateway controller already installed, plus an existing, programmed `Gateway` object
  to reference.
- If terminating TLS with cert-manager: cert-manager already installed — the chart
  does not install or depend on it.
- If planning `replicaCount > 1`, or an HPA whose `minReplicas` exceeds 1: a reachable
  Redis (in-cluster or external) already decided.
- If planning CPU-based autoscaling: Kubernetes Metrics Server installed; if
  additionally scaling on active WebSocket connections, a custom-metrics adapter (for
  example Prometheus Adapter) configured to expose the relay's gauge as a pod metric.
- If enabling the optional `ServiceMonitor`: the Prometheus Operator's CRDs and
  controller already installed.
- A StorageClass supporting `ReadWriteOnce`, if the git working-state PVC is left
  enabled (the default) rather than the ephemeral `emptyDir` alternative.

## Prepare and verify the cluster

1. Confirm cluster access and API support. Run `kubectl cluster-info` and
   `kubectl api-resources`, and confirm the cluster serves `autoscaling/v2`
   (HorizontalPodAutoscaler) and `policy/v1` (PodDisruptionBudget) if either is
   planned — the chart's `Chart.yaml` declares no `kubeVersion` floor of its own, so
   the cluster's own API surface is the only gate.
2. If choosing Gateway API over classic Ingress, confirm the
   `gateway.networking.k8s.io/v1` CRDs and a Gateway controller are already installed,
   and identify or create the `Gateway` object that `httproute.parentRefs` will
   reference. Gateway API is not part of core Kubernetes; installing its CRDs and a
   controller is a separate, cluster-wide step this chart does not perform.
3. Create the target namespace the release will live in — for example
   `kubectl create namespace <ns>`, or the `--create-namespace` flag the chart's own
   README quickstart command passes to `helm install`. No template in this chart
   renders a `Namespace` object itself.
4. For a production install, create the Secret that `secrets.existingSecret` will
   name, populated with whichever of `BUZZ_RELAY_PRIVATE_KEY`,
   `BUZZ_GIT_HOOK_HMAC_SECRET`, `DATABASE_URL`, `READ_DATABASE_URL`, `REDIS_URL`,
   `BUZZ_S3_ACCESS_KEY`, `BUZZ_S3_SECRET_KEY` and `BUZZ_KLIPY_API_KEY` the deployment
   needs — schema in the chart's `examples/secret-sample.yaml` — through whatever
   secret-management tool keeps its unencrypted form out of git. Do this before
   install: the chart's own generated-Secret fallback is explicitly unsafe under
   GitOps (see *Boundary*), so a production/GitOps release has no working fallback if
   this step is skipped.
5. Decide the exposure path and confirm its cluster-side prerequisite exists.
   Classic Ingress: confirm the `ingressClassName` you intend to set already exists
   (`kubectl get ingressclass`), and, for long-lived WebSocket connections, plan
   generous proxy-timeout annotations — the chart's own
   `examples/ingress-cert-manager.yaml` sets `nginx.ingress.kubernetes.io/proxy-read-timeout`
   and `-send-timeout` to `"3600"` for exactly this reason. Gateway API instead:
   confirm the `Gateway` named in `httproute.parentRefs` already exists and is
   accepting routes. `ingress.enabled` and `httproute.enabled` are mutually exclusive
   — the chart fails to render if both are set — and neither is required at all; a
   platform may route to the chart's `Service` directly.
6. If terminating TLS with cert-manager, apply a `ClusterIssuer` once per cluster
   before installing the chart — the second YAML document in
   `examples/ingress-cert-manager.yaml`. Helm's value-file parser reads only the
   first document in that file, so the `ClusterIssuer` is a plain `kubectl apply`,
   never something Helm applies.
7. If the git working-state PersistentVolumeClaim is left enabled
   (`persistence.git.enabled: true`, the default), confirm a StorageClass supporting
   `ReadWriteOnce` is available — the cluster default (leave
   `persistence.git.storageClass` empty) or a named class. Each relay replica binds
   its own `ReadWriteOnce` claim; no `ReadWriteMany` class is needed at any replica
   count, because git ref/object state is object-store-backed rather than PVC-backed
   (see *See also*). For a stateless-node HA topology, set
   `persistence.git.enabled: false` instead — every replica then gets a per-pod
   `emptyDir` scratch volume and there is no PVC to provision at all.
8. Once the chart has been installed or upgraded — the Helm-side install/upgrade
   mechanics are a sibling task's scope, not this node's (see *Boundary*) — verify
   the cluster-side result: `kubectl get pods,svc,pvc -n <namespace>` for the relay
   Deployment(s) and their claims; `kubectl get ingress` or `kubectl get httproute`
   for the exposure path chosen in step 5; `kubectl get pdb,hpa -n <namespace>` if
   disruption budgets or autoscaling were enabled; and, if a pod is not becoming
   Ready, check its logs against `/_readiness` — readiness fails closed on Postgres,
   Redis or a deletion-fence schema check, not only on the shutdown flag (see *See
   also*).

explicit boundary of the private staging pipeline named in this repository's own
