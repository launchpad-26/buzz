## Executive answer

**Documentation agents do not select repository context by relevance to the claim they are about to make. They select by reachability** — what the harness loads unconditionally, what a similarity query ranks highly, what fits the attention budget, and what the working copy happens to expose. Each of those is a different quantity from *the evidence that determines whether the documented claim is true*, and the gap between them is where incomplete, irrelevant, and misleading context enters. This framing is my interpretation; the four mechanisms under it are each separately sourced below.

The sourced core is that every stage of that pipeline has a measured failure mode. Retrieval can return nothing that answers the question at all ([Barnett et al. 2024, FP1](https://arxiv.org/html/2401.05856v1)); it can hold the answer but rank it below the cut ([FP2](https://arxiv.org/html/2401.05856v1)); consolidation can drop it for budget ([FP3](https://arxiv.org/html/2401.05856v1)); assembled context degrades non-uniformly with position and length ([Liu et al. 2024](https://aclanthology.org/2024.tacl-1.9/); [Hong et al. 2025](https://www.trychroma.com/research/context-rot)); a single irrelevant clause measurably degrades reasoning ([Shi et al. 2023](https://proceedings.mlr.press/v202/shi23a.html)); and in code specifically, *stale-but-present* repository snippets do not behave as inert noise but actively steer generation toward the obsolete state ([Weng et al. 2026](https://arxiv.org/abs/2605.14478)). That context assembly is causal for documentation truthfulness — not merely for fluency — is shown directly by DocAgent's ablation: removing dependency-aware context ordering drops repository-entity truthfulness from 94.64% to 86.75% ([Yang et al. 2025, Table 5](https://arxiv.org/html/2504.08725v1)).

**On sufficiency, the decisive and counter-intuitive finding is that the output cannot certify the evidence.** Joren et al. show models answer correctly 35–62% of the time when the retrieved context is provably insufficient — parametric knowledge silently fills the gap — and that with insufficient context large models hallucinate rather than abstain ([Joren et al. 2025](https://arxiv.org/html/2411.06037v3)). Interpretation: a documentation reviewer who judges sufficiency from a correct-looking, well-cited document is measuring the wrong object. Sufficiency must be assessed on the assembled context *before or independently of* the prose, by decomposing the document into atomic claims and asking, per claim, whether a pinned repository artifact plausibly determines it.

That determination is feasible but bounded, and the bound is material to the answer. Sufficiency classification is itself model-judged and imperfect — the best autorater reported by Joren et al. reaches 93% accuracy on a QA setting ([Joren et al. 2025](https://arxiv.org/html/2411.06037v3)) — and, more seriously, **no context-side method can establish sufficiency for omission-class claims.** Detecting that a document silently failed to mention a prerequisite requires knowing what the repository contains that the agent never retrieved, which is exactly what a retrieval-scoped check cannot see. Barnett et al.'s FP1 (Missing Content) is defined by that blindness, and they conclude that "validation of a RAG system is only feasible during operation" ([Barnett et al. 2024](https://arxiv.org/html/2401.05856v1)). Practically, the achievable answer is asymmetric: **insufficiency is detectable; sufficiency is at best not-yet-falsified.** The candidate checks in this report are built around that asymmetry.

## Question, scope, and method

### Subquestions

- What forms does bad repository-context selection take — what are the distinguishable failure classes?
- By what mechanisms does an agent end up with incomplete, irrelevant, or misleading repository evidence?
- Which of those mechanisms are properties of the retrieval/selection stage, and which are properties of how the assembled context is consumed?
- What consequences follow specifically for *documentation* artifacts, as opposed to code or answers?
- How can evidence sufficiency be operationally defined for a documentation task?
- Which detection and validation methods exist, what do they measure, and what can each not establish?
- What mitigations are supported, and under what boundary conditions do they fail or reverse?
- What is the counterevidence — where is context selection *not* the bottleneck, and where does pruning context hurt?

- **Hallucination and unsupported inference once context is fixed** — topic 04.
- **Citation fabrication and circular evidence** — topic 05. The habit of reading documentation instead of the code it describes is noted here as a selection mechanism; its provenance consequences belong to 05.
- **Adversarial or poisoned context** — topic 17. All mechanisms here are assumed non-malicious.
- **Reviewer psychology and automation bias** — topic 18; **breadth of automated detection** — topic 19.

## Causes and mechanisms

### Sourced: the selection stage optimizes a proxy

Repository context selection is generally implemented as similarity search over chunks, and similarity is a proxy for relevance, which is in turn a proxy for *determination* — whether the artifact settles the truth of the claim. Barnett et al.'s taxonomy is useful precisely because it separates the proxy's failure modes: content that does not exist (FP1), exists but ranks low (FP2), ranks high but is evicted (FP3), and survives to context but is not used (FP4/FP7) ([2024](https://arxiv.org/html/2401.05856v1)). Their case studies span research, education, and biomedical domains, including a BioASQ study of 4,017 documents and 1,000 questions; the taxonomy is an experience report from one team, which bounds its generality.

For documentation specifically, the determining artifact for a claim is frequently *not* the most similar one. A claim about a function's error behavior is determined by its callers and its exception types; a claim about a default is determined by the configuration loader, not by the README paragraph that mentions the default. DocAgent's design encodes exactly this — it performs static analysis over the whole repository, parses ASTs to recover calls, inheritance, attribute access and imports, and processes components in dependency order so that context is built incrementally ([Yang et al., ACL 2025 demo](https://arxiv.org/html/2504.08725v1)).

### Sourced: context assembly is causal for documentation truthfulness

This is the claim that separates "context selection is untidy" from "context selection produces false documentation", and it is directly measured. DocAgent's ablation replaces dependency-aware processing order with a random order, holding the model fixed. Repository-entity truthfulness — the "existence ratio", defined as the proportion of unique repository-specific entities named in the documentation that correspond to actual entities in the codebase, verified against a dependency graph — falls from **94.64% to 86.75%** for the GPT configuration and **87.76% to 83.06%** for the CodeLlama configuration; helpfulness falls 3.88 → 3.44 and 2.35 → 2.18 ([Yang et al. 2025, Tables 4–5](https://arxiv.org/html/2504.08725v1)). The same metric separates architectures sharply: 95.74% for DocAgent-GPT against 61.10% for a chat baseline and 45.04% for fill-in-the-middle ([Table 3](https://arxiv.org/html/2504.08725v1)). Note the authors' own scoping: completeness was excluded from the ablation because it depends on code structure rather than processing order.

Two independent lines corroborate the direction. Shi et al. show that a single irrelevant sentence degrades performance on problems the model otherwise solves ([ICML 2023](https://proceedings.mlr.press/v202/shi23a.html)). Weng et al. show that in a repository setting the harm is not merely dilution: stale snippets *bias* output toward the superseded state, with 75% Jaccard overlap in which samples were vulnerable across two different models, suggesting a systematic rather than model-specific effect ([2026](https://arxiv.org/abs/2605.14478)).

### Sourced: harnesses preload context unconditionally

The agent does not begin from an empty context. Claude Code loads `CLAUDE.md` and `CLAUDE.local.md` from the working directory and every directory above it at launch, concatenating rather than overriding them, with imports expanded up to four hops ([memory docs](https://code.claude.com/docs/en/memory), retrieved 2026-09-08). The same documentation is explicit that this material is "context, not enforced configuration", that adherence degrades with file size, and that contradictory rules may be resolved arbitrarily. Anthropic's context-engineering guidance frames the underlying constraint: context is "a finite resource with diminishing marginal returns", and agents should prefer "just in time" loading of data via tools over pre-loading ([Anthropic Engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Interpretation: preloaded instruction files are the highest-salience, least task-selected evidence an agent holds. That combination is what makes C1 and C10 dangerous — the material is not chosen for the task, is not verified against the task, and is positioned to dominate.

Empirically, these files are also thin in predictable places. A study of 2,303 agent context files across 1,925 repositories reports coverage of testing procedures at 75.9%, implementation details at 70.8%, and architecture at 68.1%, against security at 14.8% and performance at 14.5%, and characterizes the files as evolving "like configuration code through frequent, small additions" ([Agent READMEs, arXiv:2511.12884](https://arxiv.org/abs/2511.12884), abstract-level reading only). Interpretation: an agent that grounds documentation in these files inherits their shape — well-supported on build and test mechanics, near-unsupported on security and performance properties.

### Sourced and reproducible: the view boundary can be far narrower than the repository

This worktree is a sparse checkout. The following was run at local commit `4bac39fe512c9b289992951de1222abd61d5790c` on 2026-09-08:

```
$ git ls-files | wc -l
6287
$ git ls-files | while read -r f; do [ -e "$f" ] && echo x; done | wc -l
612
$ git ls-files | awk -F/ 'NF>1{print $1}' | sort -u | wc -l
27
$ ls -d */
launchpad/
```

Of 6,287 tracked files, 612 (9.7%) exist on disk. Of 27 tracked top-level directories, one is materialized. The root `CLAUDE.md` — which is present on disk and, per the harness documentation above, loads unconditionally — describes a `crates/` tree of 23 crates, a `desktop/` tree, a `mobile/` tree and others. None of those directories exist in the working copy:

```
$ ls crates
ls: crates: No such file or directory
$ git ls-files crates/ | wc -l
476
```

The divergence is visible in search results, which is where it does real damage:

```
$ grep -rl "pub const CHANNEL_METADATA" .        # no output
$ git grep -l "39000" HEAD -- crates/buzz-core/src/kind.rs
HEAD:crates/buzz-core/src/kind.rs
```

Interpretation: an agent that establishes repository scope with filesystem tools sees a documentation-only repository; an agent that queries git objects sees a 6,287-file product repository. Both views are internally consistent and neither announces its own boundary. A documentation agent that concluded "this repository contains no Rust crates" would have assembled evidence that was complete *with respect to its view* and badly incomplete with respect to the repository — and no amount of care applied to the retrieved snippets would surface the error. This is one repository under one configuration and is offered as a demonstration of the mechanism, not as a measurement of its frequency. It also illustrates why the sufficiency question has to include a *view-completeness* component and cannot be answered purely from the retrieved set.

### Sourced and local: instruction-source conflict

This repository documents an intentional conflict between instruction sources. `launchpad/AGENTS.md` §1 states of the root `CLAUDE.md` and `AGENTS.md`: "For deployment, docs, and cohort process work, **that guidance is wrong, not merely irrelevant.** This file supersedes it for anything under `launchpad/`". The root `CLAUDE.md` carries a corresponding pointer, and both files were present on disk at the pinned commit. §3 of the same file records a second, adjacent hazard: `launchpad/AGENTS.md` (a contributor guide) and `launchpad/agents/` (persona packs) "are different things with adjacent names", and a commit hook blocks a shape that a name-based selector would otherwise produce.

Interpretation: this is a well-managed instance — the conflict is written down, scoped, and ordered. That is the exception. The general mechanism is that precedence between instruction sources is asserted *in the content of one of them*, so an agent must already have selected and read the subordinate file to learn that it is subordinate. Where the harness resolves conflicts arbitrarily (per the first-party documentation above), correct precedence depends on the agent reading the very file its default selection may skip.

### Interpretation: why documentation is a harder selection target than code

Three differences, offered as interpretation and not directly measured by any source I found:

1. **No execution oracle.** A code agent gets a test suite; wrong context often produces a failing build. Documentation has no equivalent — wrong context produces *fluent prose*, and the artifact that would have contradicted it was, by construction, not retrieved.
2. **Claims about absence and about the whole.** Documentation routinely asserts "the only supported way", "all handlers do X", "no configuration is required". Such claims are determined by the *entire* repository, not by any retrieved subset, so retrieval-based selection cannot in principle supply their evidence.
3. **Documentation is itself the most similar text to documentation.** A similarity retriever asked for context about a subsystem will preferentially surface prose *about* that subsystem over the code that implements it — the highest-similarity, lowest-authority evidence. That path is how a stale claim gets re-attested; its provenance consequences belong to topic 05.

## Detection and validation

### Defining sufficiency

The most usable formal definition comes from Joren et al.: an instance has sufficient context "if and only if there exists an answer A′ such that A′ is a plausible answer to the question Q given the information in C" ([2025](https://arxiv.org/html/2411.06037v3)). Note what this does and does not say: it is a property of the *context*, evaluated without reference to what the model produced, and it asks for plausibility-given-C rather than correctness. That independence from the output is the whole value of the construct.

For a documentation task the unit is not a question but a claim. Interpretation: the workable adaptation is *per-claim sufficiency* — decompose the document into atomic, checkable claims, and for each ask whether some pinned repository artifact in the assembled evidence plausibly determines it. This mirrors the nugget methodology used for RAG evaluation, where an answer is scored by which atomic facts it does and does not contain, and where automatic nugget assignment correlated strongly with manual assessment across 21 topics and 45 runs ([Pradeep et al. 2024](https://arxiv.org/abs/2411.09607)).

### Methods, and what each cannot establish

| Method | What it measures | What it cannot establish |
|---|---|---|
| **Sufficiency autorater** — classify the assembled context against each claim ([Joren et al. 2025](https://arxiv.org/html/2411.06037v3)) | Whether retrieved evidence plausibly determines the claim, independent of the prose | Not exact: best reported autorater accuracy 93% (Gemini 1.5 Pro, 1-shot) on QA. Cannot see artifacts that were never retrieved, so it is blind to C3 by construction. Reported insufficiency base rates on its own benchmarks were high — roughly 22.6% (FreshQA) to ~50% (HotpotQA at 6,000 tokens) — which is a caution about how often "gold" context is not actually sufficient. |
| **Entity grounding / existence ratio** — verify every repository-specific entity named in the document against a dependency graph ([Yang et al. 2025](https://arxiv.org/html/2504.08725v1)) | Whether named classes, functions, methods and attributes exist. Cheap, deterministic, repository-anchored | Existence is not correctness: an entity can exist and the sentence about its behavior still be false. Does not cover behavioral, normative, or absence claims. |
| **Context precision / context recall** ([RAGAS, EACL 2024 demo](https://aclanthology.org/2024.eacl-demo.16/)) | Retrieval-stage quality: relevance and ranking of retrieved chunks; recall against a reference | Context recall requires a reference to decompose against, so it measures against a known answer, not against the repository. Ragas' own documentation states that "calculating context recall always requires a reference to compare against" and that the metric "uses `reference` as a proxy to `reference_contexts`" ([Ragas docs, retrieved 2026-09-08](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)) — so it scores retrieval against a known good answer, which a documentation task does not have in advance. Judge-model dependence adds stability risk. I found a secondary report of context recall scoring zero despite correct, relevant retrieval in a domain-terminology setting, but could not open the underlying paper, so that claim is not carried here. |
| **Nugget recall** ([Pradeep et al. 2024](https://arxiv.org/abs/2411.09607)) | Whether the document covers the atomic facts a good answer should contain | Requires a nugget list, i.e. someone must already know what completeness means for this document. Detects under-coverage against a stated standard, never against unknown unknowns. |
| **View-completeness probe** — compare the tool-visible file set against the repository's own index (local demonstration above) | Whether the agent's evidence pool could in principle have contained the determining artifact | Says nothing about whether the right artifact was selected from within the view. Cheap and deterministic; catches C2 only. |
| **Counterfactual context ablation** — re-run with the context perturbed and diff the output ([Yang et al. 2025](https://arxiv.org/html/2504.08725v1); design mirrored by [Weng et al. 2026](https://arxiv.org/abs/2605.14478)) | Which claims actually depend on which evidence; exposes claims that survive removal of their support (C9) | Expensive, and a claim's stability under ablation is ambiguous — it may indicate robust grounding or parametric substitution. Distinguishing the two needs a further check. |
| **Operational monitoring** ([Barnett et al. 2024](https://arxiv.org/html/2401.05856v1)) | Failures that only appear against real questions and real corpora | Their explicit conclusion is that validation "is only feasible during operation" — i.e. design-time testing does not substitute. Slow, and gives no pre-publication signal. |

### The asymmetry that governs all of these

Interpretation, following directly from Barnett's FP1 and from Joren et al.'s definition being scoped to the retrieved set C: **every method above is a test for insufficiency, not a proof of sufficiency.** Each evaluates the evidence that was assembled. None can evaluate the evidence that was not. The practical consequence is that a "sufficiency check" should be reported as *no insufficiency detected*, and the residual risk — the omission classes, C3 and C8 — should be routed to the one control that can see outside the retrieval: comparison against the repository's own full index, or a human who knows the system.

A second consequence follows from C9. Because models answer correctly 35–62% of the time on insufficient context, the correlation between output quality and evidence quality is weak enough that **document review and evidence review must be separate passes.** A reviewer who reads the document and finds it accurate has not established that the agent had grounds; they have established that this time the priors were good.

## Mitigations

### Supported, with quantified effect

- **Order and build context along the dependency structure, not by similarity.** DocAgent's ablation isolates this: dependency-aware ordering is worth 7.89 percentage points of entity truthfulness (94.64% → 86.75%) and 0.44 of helpfulness in the GPT configuration ([Yang et al. 2025](https://arxiv.org/html/2504.08725v1)). Boundary: measured on Python repositories with AST-derived dependency graphs; languages and artifacts without a clean dependency graph (prose, YAML, infrastructure configuration) have no obvious analogue, and the authors explicitly did not evaluate completeness under this ablation.
- **Inject current evidence rather than only removing stale evidence.** Weng et al. find no-retrieval eliminates stale references but yields 1/17 passing completions, while adding valid current evidence alongside stale snippets largely recovers performance ([2026](https://arxiv.org/abs/2605.14478)). Interpretation: for documentation, the mitigation for a suspected-stale source is to retrieve its current counterpart and put both in context with their revisions, not to withhold the topic. Boundary: n = 17, code completion.
- **Keep the assembled context small and load just in time.** Anthropic's guidance is to treat context as finite with diminishing returns, maintain lightweight identifiers and load data via tools at runtime, and use compaction and sub-agents that return "condensed, distilled summary of its work (often 1,000-2,000 tokens)" to avoid polluting the main context ([Anthropic Engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). This is first-party practitioner guidance, consistent with C7's measured position and length effects, not itself a controlled study.
- **Prefer a lightly human-guided pipeline over more agentic machinery.** In a controlled README-generation comparison, a single-agent pipeline matched multi-agent text quality with 86% fewer tokens at twice the speed; the multi-agent system won on structural consistency (98%); and the *developer-guided planning* variant produced the best overall documentation quality ([Saleh et al. 2026](https://arxiv.org/abs/2606.30524)). Boundary: preprint, README genre only, abstract-level reading.

### Supported in direction, unquantified for this setting

- **Separate the evidence review from the prose review**, per the C9 asymmetry above. Interpretation, following from Joren et al.
- **Pin every cited artifact to a revision.** This repository already does so (`launchpad/Research/363-detecting-clean-but-wrong-merges.md` pins fork-side and upstream-side claims to distinct commits), and its own prior research records that a document under `launchpad/` sits outside the mechanical staleness detector specified for handbook pages (`launchpad/Research/343-citation-staleness.md`). Interpretation: pinning is what makes later sufficiency re-checks mechanical rather than interpretive; it does not by itself detect anything.
- **State the view boundary in the artifact.** No source I found proposes this; it follows directly from the local C2 demonstration.

### Trade-offs and where mitigations reverse

Aggressive context pruning has a real cost, and the literature was genuinely divided on it. Cuconasu et al. reported that adding *random* documents to a RAG prompt improved accuracy by up to 35%, concluding that "the underlying assumptions that fueled RAG development may be faulty" ([SIGIR 2024](https://arxiv.org/pdf/2401.14887)). That result stood as direct counterevidence to C5 for roughly two years. It has since been reproduced and bounded: the effect holds under the original setup — earlier-generation LLMs, restrictive prompting, constrained decoding — but "does not generalize to modern instruction-tuned LLMs" ([SIGIR 2026](https://arxiv.org/abs/2607.03615)). Interpretation: for current models, prune irrelevant context; but the episode is a warning that the harm of irrelevant context is *setting-dependent*, and a mitigation validated on one model generation should not be assumed to transfer.

More consequentially, **selection is not always the binding constraint.** A study of OpenHands, SWE-agent and Prometheus trajectories on SWE-Bench reports that agents identify the problematic files with 72–81% accuracy *even in failed runs*, with failure driven by the adequacy of the modification rather than by localization ([Majgaonkar et al. 2025](https://arxiv.org/abs/2511.00197); abstract-level reading). Interpretation: this is code repair, not documentation, and the analogue for documentation would be Barnett's FP4/FP7 — the agent had the right evidence and wrote the wrong document. Effort spent on retrieval quality does not address that class, and a review programme built only around context sufficiency will systematically miss it.

Finally, the checks themselves cost something. Counterfactual ablation multiplies generation cost; nugget evaluation requires authoring the nugget list; sufficiency autorating adds a judge model whose 93% accuracy means roughly one claim in fourteen is misclassified in the setting where it was measured.

## Limits and open questions

- **The transfer from QA to documentation is unvalidated.** The two most load-bearing quantitative findings — the sufficiency framework and the correct-despite-insufficient-context rate — were measured on HotpotQA, Musique-Ans and FreshQA. Documentation claims differ in kind: they are multi-claim, often normative, and frequently make assertions about absence or totality. I found no study that measures context sufficiency for a documentation task on a repository. This qualifies every sufficiency conclusion in this report.
- **Small samples on the most repository-specific evidence.** The stale-context result rests on 17 curated cases across 5 Python repositories; the RAG failure taxonomy is one team's experience report. Both are credible in direction and should not be quoted for magnitude.
- **The 35–62% figure is a single evidentiary chain.** It is the most consequential number here and I found no independent replication. Confidence in the *direction* (output correctness is a weak signal of evidence sufficiency) is high, because it is mechanistically obvious and consistent with Barnett's separation of failure points; confidence in the *magnitude* is low.
- **No measured base rate for documentation-agent context-selection failure.** Nobody has published "what fraction of agent-authored documentation claims lacked sufficient repository evidence". Without it, the value of the checks below is argued, not demonstrated.
- **Absence and totality claims may be undecidable by any retrieval-scoped method.** I could not find a proposed technique that establishes "no other code path does X" from a retrieved subset. Whether static analysis over the full index can close this for restricted claim classes is open.
- **The local observations are one repository, one configuration, one day.** The sparse-checkout demonstration is a clean existence proof of the mechanism and no evidence at all about its prevalence. I did not survey other repositories or harnesses.
- **Mutability.** Harness behavior (context-file loading, compaction, sub-agent context isolation) is product behavior that changes; the first-party citations here are dated to retrieval on 2026-09-08 and should be re-checked rather than assumed.
- **Unresolved.** Does dependency-aware context selection help for non-code documentation genres (runbooks, ADRs, deployment procedures) where no dependency graph exists? Does per-claim sufficiency checking degrade as claim granularity gets coarser? Is there a detectable signature that distinguishes a claim grounded in evidence from one that merely survived ablation because the model knew it anyway?

## Practical review checks

Research output, offered as candidates. They have not been trialled here, and none is adopted policy.

- **Declare the view.** Require an agent-authored document to state the evidence boundary it worked within — repository, revision, and whether the working copy was complete. The local demonstration shows a 9.7%-materialized working copy that announces nothing.
- **Run a view-completeness probe before authoring.** Compare the tool-visible file set against the repository index (`git ls-files`) and treat a large divergence as a blocking condition rather than a note.
- **Review evidence and prose in separate passes.** Because output correctness is a weak signal of evidence sufficiency, a pass that reads only the document cannot clear the evidence.
- **Decompose to atomic claims and require a pinned artifact per claim.** Repository path plus commit SHA, close to the claim. Claims that cannot be pinned are candidates for removal or for explicit marking as inference.
- **Flag absence and totality claims for separate handling.** "Only", "all", "never", "no configuration required" cannot be supported by a retrieved subset; route them to full-index analysis or to a human.
- **Check entity existence mechanically.** Every repository-specific identifier named in the document should resolve in the repository at the stated revision — the cheapest available grounding check, and deterministic.
- **Ask what evidence would have falsified each claim, and whether it was in context.** A sufficiency judgement that never names a possible falsifier is not a sufficiency judgement.
- **Where a source is suspected stale, retrieve its current counterpart rather than dropping the topic** — withholding evidence degraded outcomes more than mixing current with stale in the one controlled study available.
- **Report checks as "no insufficiency detected", never as "evidence sufficient."** The asymmetry is real and the wording should carry it.
- **Verify instruction precedence explicitly** when more than one instruction file is in scope, since harness conflict resolution is documented as arbitrary and precedence is asserted inside the subordinate file.
