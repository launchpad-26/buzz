## Executive answer

Agents reconstruct source-code semantics **usefully but not reliably enough to be treated as documentary authority without dimension-specific validation**. Accuracy depends more on the claim's granularity and evidence boundary than on whether the prose sounds coherent. In a 2024 study of 540 Java method comments, 18% of GPT-4 comments contained at least one demonstrably inaccurate statement; in a different 2024 study, reviewers judged 97.4% of GPT-4 explanations of unobfuscated C, JavaScript, and Python code correct. These results are not interchangeable: the former used an unforgiving whole-comment factual criterion and inspected callees, while the latter judged whether an explanation matched code functionality and included recognizable training-set code. The disagreement is counterevidence to any universal rate and demonstrates metric sensitivity. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1); [Fang et al.](https://www.usenix.org/system/files/usenixsecurity24-fang.pdf))

The strongest supported pattern is a **granularity cliff**. On CoRe Lite's short, intraprocedural functions, leading reasoning models achieved 91.74–92.56% F1 when deciding whether one dependency exists, but only 42.61–50.25% exact match when required to enumerate every dependency source. Correct-trace rates sat between those figures, and information-flow enumeration was only 15.61% for o3 and 26.73% for Gemini 2.5 Pro. ([Xie et al.](https://arxiv.org/html/2507.05269)) SemBench likewise found that its best evaluated model reached 80.42% over six static-semantic properties, ranging from 91.15% for statement dead-code questions to 64.38% for liveness through branches and loops. ([Xu et al.](https://www.nature.com/articles/s44488-026-00014-y)) These are code-analysis tasks, not long-form documentation, so they bound necessary reasoning capabilities rather than directly predict document-level accuracy.

Confidence is **high** that local behavioral claims, relation directions, and explicit literals can often be drafted correctly; **high** that non-trivial traces and complete enumerations remain error-prone; **moderate** that repository architecture recovery is useful but abstraction-sensitive; and **low** on any numerical estimate for effective defaults, error behavior across integrations, or trust boundaries in deployed systems. Source code can show declared fallbacks, handlers, data transformations, and authorization checks, but effective configuration, deployment relationships, external actors, operational failure behavior, and organizational trust decisions may live elsewhere. The practical conclusion is not “agents cannot understand code”; it is that each claim must be limited to the evidence layer inspected and validated with tools capable of checking that type of claim.

## Question, scope, and method

### Subquestions

- What direct evidence measures factual accuracy of LLM-generated code summaries or explanations?
- How does accuracy change from local classification to complete control-flow, data-flow, call-graph, and dependency reconstruction?
- What errors affect architecture, dependencies, defaults, error handling, and trust boundaries?
- Which mechanisms plausibly explain those errors, and what counterevidence challenges them?
- Which static, dynamic, architectural, and human validation methods can detect each failure, and what can each method not establish?
- Which mitigations improve fidelity without turning generated prose or an LLM reviewer into an oracle?

### Exclusions

- Code generation correctness except where execution evidence tests a claimed understanding of existing code.
- General prose quality, style, readability, and coverage unless they affect semantic fidelity.
- A synthesis of the wider 20-topic research program or adoption of repository policy.
- Claims that source code can establish developer intent, deployed state, or organizational trust assumptions when those facts are not represented in the inspected artifacts.

## Failure taxonomy

| Failure class | Description | Evidence and boundary conditions |
|---|---|---|
| Local behavior mischaracterization | Prose changes a condition, return, side effect, supported value, or purpose even when the relevant method is visible. | Kang et al. found inaccurate statements in 18% of GPT-4 method comments; one generated comment claimed a `MathException` where the code returned `Double.NaN`. This was 180 public Java methods from Defects4J, simple prompting, and a whole-comment error criterion—not current repository agents. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1)) |
| Lexical-prior substitution | An identifier, familiar library combination, comment, or memorized project pattern substitutes for executed logic. | ETF records a `getJobID()` method that simply returns `-1` but received a database-retrieval story, and categorizes identifier-name bias. Fang et al. observed GPT-4 inventing a `pandas` dependency from associated imports. Clear names also help, so lexical information is a useful but unsafe proxy. ([Maharaj et al.](https://aclanthology.org/2025.acl-long.1480.pdf); [Fang et al.](https://www.usenix.org/system/files/usenixsecurity24-fang.pdf)) |
| Missing transitive context | A summary describes only the focal snippet and invents or omits behavior supplied by callees, types, generated code, libraries, callbacks, or external services. | Kang et al.'s “lacking code context” errors required inspecting returned types and called methods; the authors warn that complete context can expand substantially. Their evidence is method-level Java, but CoRe's deliberate exclusion of interprocedural calls shows that strong intraprocedural scores do not resolve this boundary. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1); [Xie et al.](https://arxiv.org/html/2507.05269)) |
| Control-flow relation error | The document reverses dependency direction, confuses syntactic reachability with feasible execution, loses an early exit, or simplifies nested conditions. | SemBench reports large category variation and difficulty carrying constraints through branches and loops. CoRe reports up to a 49.5-point performance gap from complex control structures, length, and backward/non-sequential patterns. Both use bounded program-analysis questions, not prose. ([Xu et al.](https://www.nature.com/articles/s44488-026-00014-y); [Xie et al.](https://arxiv.org/html/2507.05269)) |
| Data-flow and completeness error | The agent detects one plausible flow but omits sources, implicit flows, aliases, or intermediate steps; an incomplete graph may still support fluent prose. | On CoRe Lite, o3 scored 92.56% overall dependency-classification F1 but 42.61% exact match for complete source enumeration; its information-flow enumeration was 15.61%. CoRe is limited to 21–100-line intraprocedural functions with no non-library calls, so real repository data flow is not shown to be easier. ([Xie et al.](https://arxiv.org/html/2507.05269)) |
| Call-graph and dependency distortion | The document omits or invents call edges, collapses compile-time, package, runtime, service, and optional dependencies, or mistakes import presence for behavior. | In a separate Java evaluation, GPT-4o call-graph generation had Jaccard similarity 0.121 and chain accuracy 0.00011; in-context examples did not materially improve it. Fine-tuned CodeLlama performed much better on pair metrics but still only 0.22 chain accuracy, showing task-specific training can help without solving complete chains. ([Su and McMillan](https://arxiv.org/html/2505.12118)) |
| Architecture abstraction mismatch | Agents select the wrong C4 level, split or merge components inconsistently, omit relationships, or describe runtime/deployment structure from code-level organization. | A 2026 master's thesis comparing three terminal agents on two large open-source systems found meaningful but moderately and variably accurate C4 container views; abstraction-level misalignment dominated errors, and no post-reflection agent difference was statistically significant. This is recent student research with only two systems, so confidence is moderate. ([Qvarlander](https://bth.diva-portal.org/smash/get/diva2%3A2040623/FULLTEXT02.pdf)) |
| Default collapse | A document reports a source literal as “the default” without naming precedence, environment, version, unset/empty semantics, or runtime overrides. | No direct agent-accuracy benchmark was found. The evidence boundary is strong: Twelve-Factor defines deploy-varying configuration as separate from code, including service handles, credentials, and hostnames. Code can establish a declared fallback but not an effective deployed value when higher-precedence configuration exists. ([The Twelve-Factor App](https://12factor.net/config)) |
| Error-contract distortion | A document confuses returning a sentinel with throwing, omits transformed/rethrown errors, treats logging as recovery, or asserts retry/rollback behavior without following all handlers and dependencies. | Kang et al. provide both directions: a claimed exception where code returned `NaN`, and a claimed `null` where execution raised `UnknownKeyException`. These are direct method-level examples, not evidence about distributed retries or production recovery. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1)) |
| Trust-boundary fabrication or omission | The document infers “trusted,” “internal,” authentication, or authorization from naming/topology, or fails to model actors, data stores, sensitive data, and points where trust changes. | No direct agent-accuracy benchmark was found. OWASP defines trust boundaries at information flows where trust level changes and requires actors, processes, stores, flows, and sensitive-data classification; several of those facts may be organizational or deployment evidence rather than source. ([OWASP Security Culture: Threat Modelling](https://owasp.org/www-project-security-culture/stable/6-Threat_Modelling/)) |
| Metric-valid but semantically wrong | Similarity, entity presence, citation resolution, an LLM judge, or a passing test is treated as proof of the entire document. | Nine similarity, consistency, and self-inspection baselines in Kang et al. had no significant relationship with factual accuracy. ETF's 90.84% correct entity labels coexisted with 31.63% of whole summaries containing at least one hallucinated entity; its detector reached 73% F1, not oracle performance. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1); [Maharaj et al.](https://aclanthology.org/2025.acl-long.1480.pdf)) |

## Causes and mechanisms

**Granularity compounds error.** This is the best-supported mechanism. An agent can answer many pairwise questions correctly while failing a complete set or chain. CoRe Lite holds code and dependency categories relatively constant while changing the output obligation from classification to trace to enumeration; the large score decline is therefore stronger evidence than comparing unrelated benchmarks. At document level, ETF reports 90.84% of entity instances correct but labels 31.63% of summaries hallucinated when one entity is wrong. The interpretation is that long documentation is a conjunction of many claims: high per-claim accuracy can still produce an unacceptably high probability that at least one consequential claim is false. ([Xie et al.](https://arxiv.org/html/2507.05269); [Maharaj et al.](https://aclanthology.org/2025.acl-long.1480.pdf))

**Language priors compete with program semantics.** Identifier names, conventional library pairings, comments, and memorized repositories are often informative; Fang et al.'s 97.4% result and their observation that GPT-4 recognized Heron and jQuery are genuine counterevidence to a uniformly pessimistic account. The same study also records a nonexistent `pandas` dependency, while ETF documents a detailed database story inferred from `getJobID`. The bounded conclusion is not that models merely pattern-match, but that plausible priors can override contradictory local evidence and make errors sound natural. ([Fang et al.](https://www.usenix.org/system/files/usenixsecurity24-fang.pdf); [Maharaj et al.](https://aclanthology.org/2025.acl-long.1480.pdf))

**Relational state is harder than syntax or local labels.** SemBench's liveness weakness, CoRe's trace/enumeration decline, and Su and McMillan's poor unfine-tuned call/data-flow graphs independently point to difficulty preserving direction, order, branch constraints, and completeness. The studies differ in languages, models, and ground truth, which reduces the likelihood that one benchmark format alone explains the pattern. However, their tasks remain mainly function- or graph-level; applying the mechanism to whole repositories is a reasoned extrapolation, not a measured rate.

**The input may not contain the claimed fact.** A repository checkout can expose source defaults, dependency manifests, and authorization logic, but effective behavior is bound later by build flags, generated code, environment configuration, deployment topology, identity systems, data policy, and external service behavior. C4's own guidance assigns component recovery to static code analysis, container relationships to logs or OpenTelemetry, deployment views to infrastructure-as-code or cloud configuration, and system context to service catalogs. This is positive evidence that code is appropriate for some architecture levels and insufficient for others. ([C4 model FAQ](https://c4model.com/diagrams/faq)) A model cannot faithfully reconstruct an absent fact; it can only abstain, label an assumption, or retrieve another evidence layer.

**Fluency and readability obscure validation weakness.** Fang et al. provide another useful counterexample. Their reviewers judged GPT-4's unobfuscated explanations highly accurate, yet on a separate semantic-preserving de-obfuscation task only 19% of GPT-4 outputs compiled and 4% produced correct results, while the authors observed better readability. That task is generation rather than documentation and obfuscated code is an extreme condition, so it does not negate the explanation result. It does show that readable semantic narratives and mechanically preserved behavior are distinct constructs. ([Fang et al.](https://www.usenix.org/system/files/usenixsecurity24-fang.pdf))

## Detection and validation

Validation should start by decomposing a document into atomic claims and assigning each to an evidence layer. The following methods are complementary; none certifies the entire document.

| Method | Best at detecting | What it cannot establish |
|---|---|---|
| Revision-pinned claim ledger and source spans | Unsupported entities, wrong literals, wrong paths, uninspected claims, and drift between documented revision and code | A resolving path or cited span does not prove the interpretation; source may omit runtime state or intent |
| Parser, compiler, type checker, symbol index, and manifest resolver | Declared entities, types, imports, feature flags, call candidates, package versions, syntax, and build-time relationships | Feasible runtime paths, reflection/dynamic dispatch in general, external behavior, effective configuration, architectural intent, or trust |
| CFG, call-graph, data-flow, taint, and program-slicing tools | Relation direction, reachability approximations, def-use chains, sources/sinks, and omitted branches | Perfect soundness and precision for all languages and dynamic features; NIST notes undecidable limits and that complex vulnerabilities can defeat static analyzers. ([Black](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=901506)) |
| Documentation-derived property and negative tests | Concrete claims about inputs, outputs, exceptions, side effects, and selected defaults | Completeness or intent; generated tests can invent properties. Kang et al.'s detector peaked at ROC-AUC 0.67 and a threshold that removed 46% of inaccurate comments also rejected 28% of correct ones. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1)) |
| Runtime traces, coverage, failure injection, and end-to-end tests in a named environment | Actual executed paths, effective configuration, retries, timeouts, service calls, and observed identity/data transitions | All possible inputs or deployments; one passing trace is evidence for that run, not universal behavior |
| IaC, deployment manifests, service catalog, lockfiles, runtime configuration, telemetry, and threat model reconciliation | Deployment architecture, dependency resolution, effective defaults, external actors, stores, trust zones, and cross-service flows | Undocumented organizational intent or controls not present in the artifacts; stale operational artifacts still need revision/date checks |
| Maintainer or domain-owner review against ADRs and policy | Intended purpose, correct abstraction level, supported-use constraints, risk ownership, and trust classifications | Mechanical truth by itself; reviewers can share the same assumption or overlook a path |
| Independent LLM review or self-reflection | Cheap triage, suspicious-claim localization, format checks, and possible over-generation reduction | Proof. Kang et al.'s self-inspection baseline did not predict factual accuracy, while Qvarlander found self-reflection benefits depended on the agent and mainly reduced hallucination for over-generating agents. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1); [Qvarlander](https://bth.diva-portal.org/smash/get/diva2%3A2040623/FULLTEXT02.pdf)) |

Static and dynamic validation answer different questions. Static analysis can inspect paths independent of a chosen execution but faces exponential interactions, modeling approximations, and undecidability; tests can reveal unexpected runtime failures but only for exercised inputs and environments. NIST therefore describes testing and static analysis as complementary. ([Black](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=901506)) For code-derived documentation, the required boundary statement is: *which revision and artifacts were analyzed, which semantic properties were mechanically checked, which environment was executed, and which claims remain inferred*.

## Mitigations

1. **Generate an evidence map before prose.** Record each proposed claim's revision, artifact, symbol or configuration key, evidence type, and confidence. Split compound claims. This counters the whole-document failure mode and makes unverified completeness visible; it adds review cost proportional to claim count.
2. **Constrain claims to the inspected layer.** Prefer “the source fallback is 30 seconds when `X` is unset in this function” over “the production timeout defaults to 30 seconds.” Prefer “the static call graph contains a possible edge” over “requests always call.” This improves honesty but may produce less satisfying documentation.
3. **Retrieve semantic neighborhoods, not just matching snippets.** Include callers, callees, implementations, generated-code origins, manifests/lockfiles, tests, config precedence, and relevant handlers. Kang et al. support the importance of callee/type context, but also caution that more context is not a panacea because models mischaracterize visible code too. ([Kang, Milliken, and Yoo](https://arxiv.org/html/2406.14836v1))
4. **Use deterministic analysis for structure and the agent for explanation.** Feed compiler-resolved symbols, typed dependency edges, CFG/data-flow results, and exact source spans into generation. CoRe's semi-automated ground truth and ETF's parser-plus-LLM detector support hybrid workflows; ETF still achieved only 73% F1, so the hybrid output remains reviewable evidence rather than certification. ([Xie et al.](https://arxiv.org/html/2507.05269); [Maharaj et al.](https://aclanthology.org/2025.acl-long.1480.pdf))
5. **Turn behavioral claims into executable checks.** Derive boundary, negative, and failure tests for returns, exceptions, side effects, retry conditions, and explicit default precedence. A failing claim-derived test is strong local counterevidence; a pass is narrower because the translation and path coverage may be incomplete.
6. **Join source with runtime and governance artifacts.** Validate container/deployment relationships against telemetry and IaC, effective defaults against named environment configuration, and trust boundaries against data-flow/threat models and data classification. This is necessary when the fact is not encoded in source; it also increases access, freshness, and confidentiality obligations.
7. **Require per-dimension abstention and uncertainty.** An agent should say when it cannot resolve dynamic dispatch, configuration precedence, an external service contract, or trust classification. This trades apparent completeness for lower fabrication risk.
8. **Review high-risk relations explicitly.** Human review should target negation and quantifiers (`always`, `never`, `all`), direction of dependency, source/sink identity, early exits, sentinel-versus-exception behavior, catch/rethrow/retry paths, default precedence, and changes in trust level. These are candidate controls derived from the observed failure shapes, not validated policy.

## Limits and open questions

- **No universal percentage.** Published estimates differ because “accuracy” ranges from rough functionality match to zero-false-phrase whole-summary accuracy, and because models, prompts, repositories, context windows, and agent tools change. The 97.4% and 82% GPT-4 whole-output figures should be read as method-specific bounds, not a combined estimate.
- **Documentation evidence is narrow.** Kang et al. evaluate Java public-method comments; ETF evaluates 411 Java snippet summaries and explicitly does not measure completeness or conciseness. Neither measures an agent exploring a full contemporary repository.
- **Static-semantics evidence is necessary but indirect.** CoRe, SemBench, CRUXEval, and Su and McMillan evaluate reasoning prerequisites rather than finished documentation. CoRe excludes interprocedural calls and caps functions at 100 lines; SemBench's main benchmark is C; CRUXEval uses 3–13-line generated Python functions. CRUXEval's best GPT-4 chain-of-thought setup reached 75% input and 81% output prediction, useful counterevidence that small-program execution can be strong but not solved. ([Gu et al.](https://arxiv.org/abs/2401.03065))
- **Architecture evidence is immature.** The strongest directly relevant agent study found in this review is a 2026 master's thesis on three agents and two systems. Its positive result supports exploratory use, but not broad automation claims. More multi-repository evaluations with independently adjudicated, viewpoint-specific ground truth are needed.
- **Defaults and trust boundaries are unmeasured here.** The report found authoritative reasons why code may not contain effective deployed defaults or trust decisions, but no direct benchmark quantifying how often repository agents document them correctly. Research should sample real systems, pin source plus deployment evidence, and score declared versus effective defaults and code-visible versus governance-defined boundaries separately.
- **Ground truth is itself fallible.** Expert annotation showed 87% agreement in Kang et al., 0.72 Cohen's kappa on ETF's doubly reviewed subset, and 87.5% agreement in CoRe annotation. Architecture “ground truth” particularly depends on viewpoint and abstraction. Disagreement should be retained, not silently converted into model error.
- **Contamination and evaluator coupling remain plausible.** Kang et al. could not know GPT-family training data; Fang et al. directly observed recognition of popular repositories. LLM-as-judge and self-review can share model priors with the generated document. Executable/compiler evidence and blinded human adjudication reduce, but do not eliminate, these threats.
- **Open question:** do repository agents with tool use, iterative retrieval, and current reasoning models close the completeness gap, or merely make more claims? A useful evaluation must report claim precision and recall, relation/trace completeness, unsupported-claim rate, and cost—not only reader preference or prose similarity.

## Practical review checks

- Candidate check: pin the analyzed revision and list every non-source artifact used—tests, manifests, lockfiles, generated code, IaC, runtime config, telemetry, ADRs, and threat models.
- Candidate check: break the document into atomic behavior, control-flow, data-flow, architecture, dependency, default, error, and trust claims; require a source span or explicit `inference`/`unknown` label for each.
- Candidate check: compare every `all`, `always`, `never`, “default,” “trusted,” and “internal” claim with its exact scope, precedence rules, and environment.
- Candidate check: mechanically resolve named entities and dependencies; distinguish import/build/package edges from runtime calls, network dependencies, and optional integrations.
- Candidate check: inspect callers, callees, implementations, callbacks, generated code, and error handlers before accepting a focal-function summary.
- Candidate check: compare claimed control/data-flow direction and complete source/sink sets with available CFG, call-graph, data-flow, or taint-analysis output; document the analyzer's language and dynamic-dispatch limits.
- Candidate check: execute representative positive, boundary, negative, and failure-path tests derived from behavioral, default, and error claims; record the exact environment and coverage.
- Candidate check: reconcile architecture views by level—code/components from static structure, containers from runtime/service evidence, deployment from IaC/environment, and context from service catalog and stakeholders.
- Candidate check: for every trust boundary, name the actors, process/store endpoints, data, trust-level change, identity/control, and evidence source; reject topology or naming alone as proof of trust.
- Candidate check: use independent LLM review only for triage, then require deterministic or human evidence for consequential findings and retain unresolved disagreement.
