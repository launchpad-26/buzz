# ADR-0027 — The knowledge crate splits its surface; free-text search is deferred

## Decision

**Option D.** The shipped Rust crate serves two front doors over the one committed
corpus, and neither one runs the Python pipeline live:

- **Human surface (Settings help).** Pre-rendered pages, generated by the pipeline and
  committed alongside the corpus. The crate renders them; it does not compute them.
- **Agent surface (`knowledge.*`).** A bounded, keyed record set — per symbol, per file,
  per area, per task — pre-rendered the same way. The crate looks records up; it does not
  resolve them.

**`knowledge.find(query)`'s free-text search is out of scope for the v1 crate.** It is
the one method among #211's seven with an unbounded input domain — the other six are
already keyed on a symbol, an area, or a task name — and there is no finite set of
answers an offline pipeline could pre-render against arbitrary text. It is tracked
separately as #1400 rather than solved here.

`knowledge.ask(text)` shares the same fate for the same reason: it is an eighth public
function, not one of the seven named by `all_methods()`, and it takes arbitrary
natural-language text that it routes to `find` for the FIND intent
(`knowledge.py:370-420`). #1400 covers it alongside `find`, not as a separate gap to
rediscover later.

This rejects Option A (re-implement resolution in Rust) and Option C (a live sidecar),
and it is deliberately the same shape as Option B, made explicit: the pipeline's output
is split into two committed artefacts by *audience* (human page, agent record) rather
than presented as one undifferentiated corpus.

**Ruling 11** ("the crate re-derives nothing") and **Ruling 12** ("the corpus is a
committed artefact; the desktop build does not run the pipeline") are both ratified by
this decision, unchanged from how PRD #4 stated them. **#533's success criterion is not**
— "an agent can query the corpus through `knowledge.find`, `.explain`, `.dependencies`,
`.impact`, `.setup`, `.conventions` and `.history`" is now inaccurate for `find`, and
#533 needs its own follow-up edit narrowing that promise to six methods plus a tracked
deferral, rather than being left to read as still current.

## Context

PRD #4 asserted three things that cannot all hold at once: the crate re-derives nothing
(Ruling 11), the corpus is a static committed artefact (Ruling 12), and an agent can call
`knowledge.find` with arbitrary free text (#533). `find`'s implementation, merged in PR
#573, resolves at call time over a live semantic index
(`launchpad/project-intelligence/knowledge.py:49-51`) — there is no way to pre-render an
answer to a query that has not been asked yet.

Two independent passes hit this from different directions without knowledge of each
other: this issue, and PR #577's `CONTRACT.md` §9.2, which called it "the largest
unresolved question in M3." Both found the same fork in the road. #577 framed it as a
choice between two workable designs; it is narrower than that, because Ruling 11
forbids one of the two branches outright.

Four options were considered:

- **A — re-implement resolution in Rust.** Keeps the full seven-method promise, but
  Ruling 11 forbids it in terms, and it duplicates roughly 16 test files' worth of
  provenance-critical logic in a second language — one the Python suites guarding that
  logic do not cover, and those suites currently run in no CI job at all (#270).
- **B — bounded key set, `find` deferred.** Ruling 11 and Ruling 12 both hold unchanged;
  #533 is narrowed. This is the substance of the decision; D names it more precisely.
- **C — resolution runs outside the shipped crate.** Keeps the full query surface via a
  live service, at the cost of contradicting Ruling 12 in spirit and making a help tool
  depend on availability to answer basic questions offline.
- **D — split the surface (chosen).** B, with the two front doors — human page, agent
  record — named explicitly rather than left as one undifferentiated corpus shape. #553
  can now define the record format as that split's serialisation, and #551 can scaffold
  the crate against it without unstated assumptions.

## Consequences

**Good.** #551, #552 and #553 stop depending on an unstated boundary. #553's corpus
format is decidable, because it is the serialisation of a split that is now drawn.
Rulings 11 and 12 get the ratification PRD #4 already said they needed.

**Good.** The gap between what #533 promised and what ships is bounded and named here,
rather than silently discovered later by whoever reads the PRD against the product.

**Bad, stated plainly.** #211 is already merged, and its `find` method — the one built
to answer free text at call time — will sit unused on the shipped side of this
boundary. That is real, tested work that this decision does not delete but also does not
expose. Options A and C would have used it; both cost more than this decision accepts.

**Bad.** #533 now reads as inaccurate until its own follow-up edit lands. That edit is
work this ADR creates rather than performs — per the ADR template's own rule, a decision
record is not a work item.

## Security implications

This sets where the provenance boundary is enforced, which makes it a security decision
and not only an architectural one.

`launchpad-26/buzz` is public and its desktop builds are distributed, so whatever the
crate ships reaches a wider audience than the private handbook it inherits from — PRD #4
already states this. Keeping enforcement in the pipeline (Option B/D) rather than moving
it into the crate (A) or a service (C) matters for two reasons already on record in this
issue:

1. **Provenance stays structural, not prose.** #211's review found that a multiline
   `TEAM_KNOWLEDGE` statement could forge a `FACT` line if provenance were stored as text
   rather than as a structural field on `MemoryEntry`. A re-derivation in a second
   language (A) or a service response (C) both create a second place that rule would need
   to be re-enforced, outside the Python suites that currently validate it.
2. **The audit stays at the pull request that changes the corpus**, per Ruling 12. Split
   surface or not, both committed artefacts (human page, agent record) go through the
   same review a corpus change already requires — nothing here adds a second path that
   bypasses it.
