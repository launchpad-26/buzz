  Buzz **does** implement NIP-10 positional markers, in one shared parser:
  `crates/buzz-core/src/nip10.rs`. It exposes `ThreadMarkers { root, reply }`,
  `parse_thread_markers`, `parse_thread_markers_from_parts`, and
  `ThreadMarkers::resolve()`. Read in full (197 lines).
    - Only `e` tags with `parts.len() >= 4` and a 64-ASCII-hex id at `parts[1]`
      are considered; the marker is read from `parts[3]`.
    - `match parts[3] { "root" => …, "reply" => …, _ => {} }` — the third NIP-10
      marker, `mention`, falls into `_ => {}` and is **not** parsed. Confirmed
      repo-wide: `grep -rn '"mention"' --include=*.rs crates/` returns exactly one
      hit, `crates/buzz-cli/src/lib.rs:396`, which is a `--mention` CLI flag, not
      a tag marker.
    - `resolve()`: `root`+`reply` -> `(root, reply)`; `reply` only ->
      `(reply, reply)`; `root` only or neither -> `None` (top-level).
    - A bare, unmarked `["e", <id>]` tag yields no markers at all
      (`bare_e_tag_without_marker_is_ignored` test in the same file).

  The `e` tag is **not** only a threading marker. Read directly in
  `crates/buzz-relay/src/handlers/ingest.rs`: reactions (`KIND_REACTION`)
  take their target from the **last** `e` tag and are rejected without one
  (`"invalid: reaction must reference a target event via e tag"`);
  `derive_reaction_channel` derives a reaction's channel from that target;
  standard deletions (`KIND_DELETION`) derive channel the same way; deletion
  events must carry `e_count + a_count == 1`. `KIND_STREAM_MESSAGE_EDIT`
  (`validate_edit_ownership`) requires an `e` tag naming the edit target.
  `crates/buzz-relay/src/handlers/side_effects.rs`'s `has_e_tag` keys NIP-09
  routing on the tag's *presence*, not on a decodable id.
