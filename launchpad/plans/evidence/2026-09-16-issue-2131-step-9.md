# Phase 1b evidence — STEP 9: `$PROFESSOR_VERIFIER_CMD` resolution and its failure modes

Plan: `launchpad/plans/2026-09-15-issue-2131-professor-verify-claims.md`
Branch: `feature/2131-professor-verify-claims`
Date: 2026-09-16 · Closes #2142

Six scenarios. **Every one runs the full `draft-page` gate path** — `check-page`, then
`screen-content`, then `verify-claims` — against the same draft, and observes the target
path before and after. None is a bare dispatch call. The draft is the one from STEP 8,
whose citation resolves correctly and whose claim is false, so the first two gates always
pass and the scenario under test is the only thing that can vary the outcome.

The `verify-claims` half is a reference implementation of that skill's own prose: §2a
(resolution and the exact unset message), §2b (the response grammar), §2c
(non-completion), §2d (a verdict contradicting its reason). **§2a's message is read out of
`SKILL.md` at runtime rather than copied into the runner**, so the evidence cannot drift
from the contract it claims to implement.

Target path throughout: `launchpad/agents/the-professor/library/locating-a-finding.md`.
**Absent before and after in all six scenarios.**

---

## 1. Unset — fails loud, does not skip

`check-page` passed, `screen-content` passed, and the gate then refused to proceed. It
emitted §2a's message verbatim:

```
verify-claims: $PROFESSOR_VERIFIER_CMD is not set. This gate dispatches one
independent check per claim and cannot run without it -- set
$PROFESSOR_VERIFIER_CMD to a headless, single-turn CLI command (the suite applies
no default; `claude --print` is the recommended value) before drafting.
```

This is the fail-loud shape, **not** a generic empty-command crash: it names the
variable, says what the gate needs it for, states that the suite applies no default, and
names the recommended value. **No dispatch was attempted, and the gate did not pass** —
an unresolved verifier blocks rather than being treated as "nothing to check".

## 2. A configured command that is not `claude --print` — resolves and returns a real verdict

`$PROFESSOR_VERIFIER_CMD = codex exec --skip-git-repo-check`

A different vendor's headless CLI, chosen over a stub on purpose: a stub would prove the
variable is read, but not that the contract survives contact with a second real model.

```
The span shows a newline count plus one, with no bounds check or explicit ValueError and no guarantee that the resulting line number exists in the file.
NOT_SUPPORTED
```

→ parsed by §2b as **`NOT_SUPPORTED`**, blocking correctly. The grammar held against a
model that had never seen it before, with no per-vendor accommodation. (`--skip-git-repo-check`
is required only because the verifier runs from an empty directory outside any
repository, which is the isolation §2 asks for.)

## 3. Command not on PATH — fails at launch

`$PROFESSOR_VERIFIER_CMD = definitely-not-a-real-verifier-9f3a --print`

```
gate verify-claims   LAUNCH FAILED — FileNotFoundError: No such file or directory
```

No verdict was ever produced, and none was invented. **BLOCKED.**

## 4. Runs to completion, returns prose with no recognisable verdict

The degrade that matters: nothing crashes, exit status is 0, and a careless reading could
treat the output as agreement.

```
I had a look at the code you pasted and I think the claim is basically fine,
though it depends what you mean by 'bounds'. Happy to dig further if useful!
```

→ §2b parse failure: *line two is not equal to any verdict literal*. **BLOCKED.** Note
what the prose says — "the claim is basically fine" — which is the reading a
substring or sentiment-based rule would have turned into a pass.

## 5. Well-formed `SUPPORTED`, then a non-zero exit

```
The span states exactly what the claim asserts.
SUPPORTED
```

exit 1 → §2c: **BLOCK, and the stdout is not read at all.** Completion is judged
independently of content, so a flawless verdict from a command that failed is not a
verdict.

## 6. Well-formed `SUPPORTED`, then a hang

Identical stdout, then `sleep 3600`. The dispatching agent applied the bound and killed
it → §2c: **BLOCKED on the timeout, stdout not read as a verdict.**

The bound used here was **5 seconds, not §2c's documented 120**, purely so the
demonstration terminates promptly; the mechanism under test is the bound being applied at
all and turning a hang into a block rather than an indefinite wait. §2c's default is
unchanged.

---

## What scenarios 3, 4 and 6 do and do not demonstrate

They demonstrate **the consequences of a harness whose configured verifier is not a
working headless single-turn CLI** — one that is absent, one that answers in prose it was
never asked for, one that never terminates. In each case the gate fails closed: it
blocks, it names why, and it never converts a non-answer into a pass.

**They do not demonstrate the absence of a headless CLI, and they do not solve it.** The
redesign doc names that limitation as real and unresolved — a harness with no headless
single-turn CLI at all cannot run this mandatory gate. What is shown here is that the
failure is safe and legible, not that the limitation has been removed.

## Why these six and not fewer

Scenarios 5 and 6 exist because §2b alone governs only what stdout *says*. Both print a
verdict that is perfectly well-formed by that grammar. Without §2c judging completion
separately, both would have passed the gate — a command that failed and a command that
never finished, each authorising a write.
